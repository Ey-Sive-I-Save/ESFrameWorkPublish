# ES 保留式重构合同

本合同适用于对 ES 编辑器框架、自动化入口、AI 协作层和既有工具链的升级。
目标是“增加治理能力而不替换 ES 身份”，不是把 ES 改造成另一套框架。

## 不可变兼容面

- 保留现有公开类型、菜单入口、Unity 资产路径和常用调用方式。
- 既有 `ESAutomationCenter`、`ESAutomationFacade`、`ESAIBrainCoordinator`、`ESAutomationAiBridge` 的职责边界继续有效。
- 旧调用方在没有明确迁移标记时，不得被迫改用新 API。
- 默认行为、序列化字段和窗口生命周期不能因治理接入而静默改变。

## 允许的增强方式

- 在入口外增加 Facade、Contract、Verifier、Receipt、Cache 和 Adapter。
- 对旧入口增加委托、审计、授权和证据绑定；不得复制出平行执行权威。
- 新字段必须可选、可回退，并保持旧数据可读取。
- 新验证器优先做静态深度回放；运行时验证只覆盖静态无法证明的外部事实。

## 破坏性变更门槛

删除、改名、改变默认语义、改变序列化格式或改变权限边界时，必须同时提供：

1. 迁移说明和影响范围；
2. 旧入口到新入口的映射或兼容适配器；
3. 正向、拒绝、回滚和旧数据回读用例；
4. 新旧行为差异的 Receipt；
5. 明确的弃用周期和回退路径。

缺少任一项时，变更只能停留在候选层，不得标记为 Accepted/Released。

## 验收语义

“静态通过”只证明源码、合同、边界和确定性回放成立；不宣称 Unity 实机、视觉、性能或外部进程行为。
“运行时通过”只能在获得当前任务绑定的授权包后成立。两条证据轴必须分别记录，禁止用加权总分掩盖缺失的硬门禁。

## 回退原则

重构应优先采用可逆提交、候选目录和适配层。发生失败时，先停用新增治理层并恢复旧入口；不得通过删除用户资产或重写整个 ES 模块来“修复”问题。
