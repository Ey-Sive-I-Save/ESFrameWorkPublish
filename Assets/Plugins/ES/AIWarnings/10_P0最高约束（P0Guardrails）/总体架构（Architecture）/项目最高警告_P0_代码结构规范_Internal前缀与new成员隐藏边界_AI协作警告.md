# P0：代码结构规范、`Internal_` 前缀与 `new` 成员隐藏边界

> 状态：现行 P0 约束。  
> 适用范围：所有 ES 自有 C# 类型的继承、成员可见性、内部入口命名、API 收口与结构重构。  
> 核心目的：代码结构表达真实职责与生命周期，不能为了让普通用户“不使用某方法”而扭曲结构。

## 最高结论

1. 禁止滥用 C# `new` 成员修饰符隐藏继承成员。成员隐藏不会移除基类 API，也不会形成可靠的访问控制；调用方改变静态类型后仍可能访问被隐藏成员。
2. 仅因为“不希望普通用户使用某方法”，禁止强制改成组合、额外只读 View、`internal` 外壳、重复接口、转发包装、拆分程序集或其他结构。继承、组合、访问级别和程序集边界必须由真实职责决定。
3. ES 自有、因兼容或框架扩展仍对普通调用方可见、但不面向普通业务的真实入口，统一使用 `Internal_` 前缀直接命名，例如 `Internal_Clear`、`Internal_Inject`、`Internal_Register`。
4. `Internal_` 是 ES 的语义警示和协作规范，不是 C# 访问控制。普通业务、策划代码和高频调用方禁止调用；底层实现、框架扩展和测试可以在明确职责内调用。私有实现细节和已经由语言访问级别清晰隔离的普通辅助方法不要求机械添加该前缀。
5. 不得为了补上 `Internal_` 再造一层只转发一次的包装。应重命名真实入口并迁移调用方；若入口来自 Unity、BCL 或第三方且无法改名，则保留外部合同并在 ES 领域入口处明确使用边界。
6. 本规则约束新增和修改代码。存量 `new` 隐藏与伪收口在相关调用链被触达时迁移，禁止无授权全仓机械改名。

## `new` 的判定范围

本规则默认禁止的是成员声明上的隐藏修饰符：

```csharp
public new void Inject(...) { ... }
public new bool TryRemove(...) { ... }
```

以下用法不受本规则影响：

- 对象创建：`new EntityTransformMap()`；
- 泛型构造约束：`where T : new()`；
- 数组、集合、委托或其他正常实例创建；
- 按基类正式虚方法合同实现的 `override`；
- Unity 或第三方框架明确要求、且必须维持同语义合同的成员隐藏窄例外。

窄例外必须同时说明外部合同、调用时静态类型、隐藏后语义与测试证据。不得以“编译器允许”“消除警告”或“看起来更安全”作为理由。

## 标准写法

```csharp
// 不符合：试图用 new 让普通用户看不到底层写入口。
public new TData Inject(ConfigKey key, TData data) { ... }

// 符合：真实底层入口直接表达其 ES 使用边界。
public TData Internal_Inject(ConfigKey key, TData data) { ... }

// 符合：普通业务入口使用领域语义，不重复隐藏基类成员。
public TData InjectWithDefaults(ConfigKey key, Definition definition) { ... }
```

如果基类的公共成员已经被继承，派生类无法通过 `new` 将其真正关闭。此时应：

1. ES 自有且确属底层入口：在权威声明处改名为 `Internal_...`，同步真实调用方；
2. 外部合同不可改：保留该合同，不制造“已经封闭”的假象，普通业务只使用清晰的领域入口；
3. 真正需要编译期或程序集级隔离：先证明存在安全、依赖方向、序列化、生命周期所有权或发布合同要求，再设计结构边界。

## 允许调整结构的真实理由

下列理由经过调用链和影响评估后，可以使用组合、接口、访问级别或程序集边界：

- 必须阻止不可信调用方越权，命名约束不足以满足安全边界；
- Runtime/Editor 或独立程序集的依赖方向需要编译期隔离；
- Unity/Odin 序列化身份、版本迁移或 IL2CPP/AOT 需要稳定具体类型；
- 类型拥有独立不变量、资源释放、事务、并发或生命周期所有权；
- 公共发布合同明确承诺只读能力，泄漏写入会破坏兼容性或数据完整性。

“普通用户不该用”“API 列表不好看”“想让智能提示里少几个方法”本身均不是结构调整理由。

## 审查门禁

修改继承或 API 可见性前，必须回答：

1. 这里的 `new` 是对象创建，还是成员隐藏？
2. 成员隐藏是否改变了运行语义，还是只制造了访问受限的错觉？
3. 不让普通用户调用是否可以直接通过真实入口的 `Internal_` 命名表达？
4. 是否为了命名边界新增了组合、View、接口、程序集或转发层？它们有无独立职责？
5. 若必须真正隔离，具体安全、依赖、序列化或生命周期证据是什么？
6. 修改是否仅覆盖当前触达调用链，并同步声明、调用方、测试与现行 P0？

无法证明第 5 项时，不得以“收口”为由修改代码结构。发现存量冲突时应登记为触达迁移债务，不得擅自扩大为全仓重构。

## 与其他 P0 的关系

- 本规则优先约束“仅为了不让用户使用某方法”而提出的结构改造。
- 长期泛型容器的具体类型仍可因序列化、AOT、迁移或稳定领域身份成立；不得再以隐藏 `Clear/Remove` 为唯一理由增加组合或只读 View。
- 公共协议分层仍按协议权威和程序集依赖决定；不得把 `Internal_` 当作修复程序集倒置的替代品。
- `Internal_` 不得被描述为安全控制、权限隔离或编译器禁止调用。

## 验证

- 搜索当前修改调用链中的 `new` 成员声明，逐项确认合法性；
- 搜索新增 `Internal_` 名称，确认它命名的是真实入口而非无意义转发；
- 检查派生类型、基类视图和接口调用方，禁止宣称 `new` 已封闭 API；
- 检查是否为了使用边界无故增加类型、程序集或序列化结构；
- 文本修改必须通过严格 UTF-8、U+FFFD、乱码和 `git diff --check` 检查。
