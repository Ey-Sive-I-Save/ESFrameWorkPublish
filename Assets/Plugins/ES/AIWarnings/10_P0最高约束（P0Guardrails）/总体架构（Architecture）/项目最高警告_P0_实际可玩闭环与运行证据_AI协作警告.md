# 项目最高警告 P0：实际可玩闭环与运行证据

## 规则级别

P0。任何声称影响运行时玩家体验或实际业务闭环的具体业务逻辑、角色能力、生命体行为、AICommand、相机、输入、交互、视觉表现或性能工作，都必须遵守本规则。纯 Editor 工具、资源导入器、静态分析器和只读治理工具也必须遵守本规则，但按自身执行边界验收。

## 核心要求

商业级方案、抽象设计、接口数量、模块拆分和可扩展性只能作为设计参考，不能作为功能完成或稳定的证据。只要功能声称影响运行时玩家体验或实际业务闭环，就必须形成从真实操作/触发到可观察结果的完整闭环，并以 Unity 实际运行证据验收；仅有源码、静态编译、日志或抽象设计不能签收。非运行时工具应以真实工具调用、输入资产、输出结果和错误处理证据验收，不强制套用完整 PlayMode 闭环。

至少必须能明确追踪：

`玩家/系统输入意图 → 权威 Request/State/Command → 唯一执行入口 → 业务执行 → 运动与世界结果 → 动画/IK/VFX/音频/UI 反馈 → 可观察终态 → 成功/失败/取消/打断/超时/禁用/回池清理`。

任何一段只有类型、接口、Profile、Adapter、Registry、事件或日志而没有真实消费者和可观察结果的实现，均不得宣称完成。

## 玩家操作是第一验收对象

玩家最小主链必须优先可用：

- 玩家角色可以直接取得并释放控制权；输入不会被 InputService、RuntimeMode、Writer、Permit 或状态层静默吞掉。
- 相机可以旋转、跟随、避障；移动方向按相机映射；只旋转镜头时不得强制角色转身，角色转身必须由明确的移动、瞄准或业务意图驱动。
- 重复按键、输入抖动、同时输入、设备切换和焦点切换必须有明确语义。
- 成功、失败、受阻、取消、打断、超时、控制权拒绝和状态结束都必须有可观察反馈及可重置路径。

没有可直接操作的正式或专用测试场景时，只能报告“未验收”，不能用静态代码质量或架构完整度替代可玩性证据。测试场景至少应包含正式/专用角色、相机、输入、起点、目标、障碍、失败区、重置方式，以及成功、失败、取消、重入和回池的观察点；应优先复用项目现有的场景验收规范。

## 生命体行为与 AICommand

生命体行为必须覆盖完整生命周期：发现/接受、准备/进入、持续执行、成功/失败/取消/打断、表现收尾、控制权释放、资源/Lease/临时目标清理，以及回池后的安全重置和再次进入。

AICommand 必须产生真实业务结果，不能只证明“调用过”。验收时必须说明目标对象、前置条件、控制权来源、执行入口、唯一消费者、进行中状态、失败码、可观察结果、清理路径和重试/取消路径；动画播放、事件触发或日志输出不能冒充业务成功。

## 表现、流畅度与响应度

视觉效果是功能的一部分。移动、转身、瞄准、攻击、受击、攀爬、翻越、骑乘和交互等行为，都必须让动画、IK、姿态、位移、VFX、音频或 UI 与业务状态一致；失败、受阻、资源缺失和控制权拒绝不得静默。

流畅度和响应度按功能风险分级实测并记录证据。影响玩家主操作、镜头、移动、战斗、攀爬、交互或大量实体的功能，至少覆盖输入到结果延迟、相机/移动响应、动画过渡、状态切换，以及相关 Profiler 的 GC、CPU 和内存表现；低风险或非运行时功能只需验证与其风险相关的指标。某项指标确实不适用时，必须明确标记“不适用”并说明理由；声称“无性能风险”仍必须有对应证据，不能仅凭代码形态判断。

## 禁止伪完成

禁止以下做法作为完成依据：

- 只增加抽象层、接口、模块、配置或扩展点，不接通玩家主链；
- 只通过 C# 编译、Prefab 序列化、静态搜索或一次成功路径；
- 只依靠 Debug 日志证明状态成功；
- 以商业游戏名称、架构图或“未来可扩展”替代 Unity、PlayMode、Profiler 和发布证据；
- 为未来来源或场景堆叠无意义的中间转包，反而阻断输入、控制权、状态或表现闭环。

## 证据与成熟度口径

每次报告必须区分：实现事实、静态证据、Unity 编译/域重载证据、真实操作/PlayMode 证据、表现一致性证据、Profiler 性能证据、发布/IL2CPP 证据和未验证项。

对于运行时玩家体验或实际业务闭环，缺少真实运行证据时，成熟度最高只能标记为 `Verifying` 或更低；不得称为 `Stable`、“已完成”、“可交付”或“商业级已验收”。对于纯 Editor、导入器、静态分析器或只读治理工具，应提供对应工具调用和结果证据；不适用的 PlayMode、视觉或性能项可以明确标记“不适用”，不得因不适用而虚构证据。

## AI 自测、优化与风险交付责任

AI 在用户已授权的任务范围内，不得只罗列“待验证项”后停止。应主动完成可安全执行的闭环工作：追踪真实入口与消费者、检查配置和序列化、执行适用的静态检查/Unity 编译/工具调用/PlayMode/Profiler 验证，并对已定位且可在当前权限内修正的问题完成最小修正后复测。

目标是尽量把功能推进到实际可用，而不是只让代码“看起来合理”。若运行环境、外部依赖、用户操作、发布权限或当前授权边界使验收无法继续，交付必须明确列出：

- 已完成的自测、实际结果及其证据层级；
- 尚未闭环的具体节点、触发条件和对玩家/业务的影响；
- 已知风险的严重度、复现方式、临时规避方式与是否会阻断使用；
- 下一步最小验证或修正动作，以及需要新增的明确授权。

“Unity 未运行”“缺少场景”“未拿到证据”不是空泛结论：AI 必须先检查是否已有正式或专用测试场景、可用 Unity 实例、现有测试、诊断入口或低风险替代验证；确认确实不可执行后，才可标记为受阻。不得虚构通过结果，也不得在没有用户授权时擅自写入 Git、发布、删除、历史或扩大业务范围。

## 违规处理

发现业务仅完成结构而未完成闭环时，应立即标记缺失的真实消费者、执行入口、状态终态、表现反馈、清理路径或运行证据，并停止扩大抽象范围，优先补齐最小可玩闭环和专用验收场景。
