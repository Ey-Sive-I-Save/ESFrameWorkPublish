# P0：热路径容器预热与稳态 GC 边界

> 状态：现行 P0 约束。
> 规则 ID：`es.p0.runtime.hot-container-steady-gc`。
> 权威级别：Project Authority / P0。
> 路由键：`runtime-hot-container`、`container-warmup`、`steady-state-gc`。
> 适用范围：任何进入运行时高频链路的容器、索引、缓存、Registry、Queue、Set、Pool 内部缓冲、快照缓冲或类似复用结构，不以类型名、泛型形式、序列化方式或具体实现为判定依据。
> 不适用范围：未进入高频链路的编辑器作者流程、一次性初始化、低频管理操作和离线工具；它们仍须避免无界或失控分配，但不因使用泛型或集合自动承担稳态 0 GC 合同。
> 主要证据入口：具体容器源码与测试、真实消费者调用链，以及目标场景和目标平台的 Unity Profiler 采样。

## 最高结论

本规则约束的是**容器被放入高频链路后的运行方式**，不是某一个容器类型，也不是“所有泛型必须 0 GC”。

1. 是否命中本规则由调用频率、实例规模和运行位置决定，不由类型名、`<T>` 语法、是否使用 Dictionary 或是否长期序列化决定。
2. 预热完成后的常规稳态操作必须以 `GC Alloc = 0 B` 为目标；确有平台、第三方后端或业务返回值约束而只能做到低 GC 时，必须说明来源、频率、上限和实测证据。
3. 构造、首次注册、扩容、重建、批量原子提交、错误诊断和快照导出可以属于冷路径，但不得在常态帧、每个实体 Tick 或大批量实例循环中反复发生。
4. 具体容器可以采用数组、List、Dictionary、HashSet、Queue、环形缓冲、稀疏表或混合索引。P0 约束稳态分配和消费边界，不强制统一数据结构或复制某个案例的 API。

## 稳态热路径硬要求

容器进入 `Update`、`FixedTick`、KCC、StateMachine、Buff、AI、交互、对象池、Tag/ValueChange、运行时调度或同等级高频链路后，常规操作必须满足：

1. 命中、未命中、空队列、无变化和正常拒绝等业务分支不得依赖异常控制流、动态日志或临时诊断对象。
2. 不得在每次调用中使用 LINQ、反射、闭包、捕获委托、装箱接口枚举、迭代器状态机、临时数组、临时 List/Dictionary/HashSet 或字符串拼接与格式化。
3. 容量、比较器、稳定 Key、注册表、索引、复用缓冲和必要依赖必须在初始化、绑定、租出、场景加载或其他明确管理边界准备完成。
4. 容器 API 如需返回可变数量数据，核心热路径应优先写入调用方复用缓冲、提供无分配枚举方式或返回稳定只读 View；不得默认每次返回新集合或快照。
5. 容器内部无分配不能抵消调用方包装产生的 GC。Key 构造、值转换、业务回调、事件订阅和结果复制必须与容器成本一起检查，并在 Profiler 中分别归因。
6. 稳定 StringKey 进行既有字典查询可以是无显式分配操作，但热路径不得临时创建、裁剪、规范化或拼接 StringKey。领域已有 Enum、强类型 Key、RuntimeKey 或预解析 Handle 时，极限帧级路径应优先传递已解析身份。

## 冷路径允许分配，但必须有边界

下列行为可以安排在冷路径：

- 构造容器、首次建立索引、反序列化恢复、显式重建和脏数据校验；
- `EnsureCapacity`、Warmup、首次注册，以及容量耗尽后的受控扩容或存储形态转换；
- 批量替换、批量追加、候选副本、排序、压缩和原子提交；
- 冲突消息、错误日志、异常、完整快照和作者诊断；
- 加载、租出、装备切换、配置刷新、场景切换和明确低频事件中的结构写入。

“允许冷路径分配”不等于允许无界分配，也不等于按帧调用后仍可称为冷路径。某操作一旦进入常态帧或按实体重复执行，就必须预热、复用、改为增量操作或移出高频链路。

## 预热合同

进入高频运行前必须按目标容器的实际机制完成必要准备：

1. 根据可证明的稳定上限预留容量，不得用不受约束的最大值掩盖容量设计缺失；
2. 完成索引建立、反序列化校验、Key 解析、比较器初始化、池预热和订阅注册；
3. 至少执行一次与正式路径相同的命中、未命中或出入队操作，使 JIT、首次镜像建立和首次后端初始化不落入稳态采样帧；
4. 明确哪些运行期写入可能扩容、重建、改变存储形态或触发回调，并把它们安排到可预算的管理边界；
5. 缓存查询结果或只读 View 时不得建立第二份权威，必须沿用正式 Generation、Version、Handle 或生命周期合同失效。

预热 API 的名字和形态由具体容器决定。本规则不要求所有未来容器都提供 `EnsureCapacity`、`TryRebuild`、Generation 或双镜像结构；只要求它们能证明首次成本不会意外落入声明的稳态热路径。

## 验证与签收

源码检查、单元测试和生成工程编译只能证明代码形态与静态可编译性，不能签收实际 0 GC。

1. 根据容器合同分别重复采样命中、未命中、空状态、常规写入和真实业务调用链；不适用的分支应明确标记，不得用单一成功路径代表全部稳态行为。
2. 预热完成后再采样，关闭测试日志、异常注入和一次性初始化噪声，并记录调用次数、实例规模、容量、采样帧数和后端条件。
3. Unity Editor 结果只作为预检查。涉及 Player、IL2CPP 或正式发布时，必须在对应后端和目标平台复验。
4. 只有 Profiler 在声明范围内证明稳定帧 `GC Alloc = 0 B`，才能报告“该范围实际 0 GC”；否则只能报告“静态结构无已识别显式分配”“可解释的低 GC”或“待实测”。
5. 若只允许低 GC，验收必须记录每次分配字节数、触发频率、峰值、规模增长关系和不能消除的机制原因；“看起来很少”不是证据。

## 当前案例：`ESEnumStringMirrorMap`

`ESEnumStringMirrorMap<TEnum, TValue>` 是本规则的一个当前案例，不是唯一目标，也不为未来容器规定 API 模板：

- 镜像就绪且容量预热后的 Enum `Try*`/`Contains*` 查询属于应独立验证的稳态路径；
- 已规范化 StringKey 的既有字典查询可以无显式分配，但不应自动成为极限帧级路径的默认身份通道；
- 首次镜像建立、反序列化后重建、扩容、Dense/Sparse 转换、批量原子提交、冲突消息和索引器异常属于冷路径边界；
- 当前案例的 Enum/String 双别名、Generation、Dense/Sparse 镜像和具体方法名不得被复制成其他容器的 P0 必备结构。

未来新增容器只需按自己的稳定操作、首次成本、容量策略、失效合同和实测证据遵守通用规则，不需要模仿本案例。

## 禁止误读

- 禁止把本规则解释为所有泛型、所有集合或整个生命周期必须绝对 0 GC；
- 禁止仅因使用 `List<T>`、Dictionary、HashSet、Queue 或 StringKey 就判定违规；
- 禁止为了静态“零分配”删除必要的原子性、错误诊断、作者工具或清晰 API；
- 禁止用单个案例反向规定未来容器的键类型、存储形态、继承方式、序列化方式或公共方法；
- 禁止依据源码形态、Benchmark 片段或 Editor 单次采样冒充目标业务链和目标平台已经签收。

## 审查清单

1. 该结构是否真的进入高频链路，还是只因它是泛型/容器而被过度治理？
2. 稳态操作集合是什么，命中、未命中、空状态和常规写入分别如何表现？
3. 首次分配、扩容、重建、快照和诊断是否已移到明确冷路径？
4. 容量、Key、比较器、注册、池和复用缓冲是否在进入高频运行前准备完成？
5. 调用方是否通过字符串、闭包、日志、事件、结果复制或临时集合重新引入 GC？
6. 结论来自源码检查、测试、Editor Profiler、Player 还是 IL2CPP？是否把较低层证据冒充更高层签收？
