# 模块成熟度与未完成实现治理 AI 协作警告

> 状态：现行约束。
> 最后核对：2026-08-03。
> 适用范围：ESFramework 新模块、重构模块、实验功能、待验收功能，以及任何被描述为“已完成”“可用”“稳定”或“可发布”的模块。

## 最高结论

目录、类型、接口、菜单、示例或源码存在，不等于模块已经完成。模块状态必须由当前实现范围和证据共同决定；不得用 TODO 数量、完成百分比、外部 AI 报告或旧文档代替真实状态。

未开始的方向保留在提案中；开发到一半的实现必须可识别、可隔离、可回退，且不得静默渗透到稳定模块、默认初始化和正式发布链路。

## 统一状态

| 状态 | 含义 | 允许范围 |
|---|---|---|
| `Proposed` | 只有目标、约束或方案，尚未进入实现 | 仅提案与评审；不得宣称源码能力存在 |
| `Scaffolded` | 已建立最小接口或目录骨架 | 必须可编译；不得默认启用或被稳定模块依赖 |
| `Experimental` | 原型可以局部运行，但 API、数据或序列化仍可能变化 | 仅显式启用；不得作为正式兼容承诺 |
| `Implementing` | 正在实现，功能闭环尚未完成 | 必须列出已完成范围、未完成范围和当前阻断 |
| `Integrating` | 主实现存在，正在接入配置、生命周期、资源或其他系统 | 必须审计跨模块依赖、初始化和退出路径 |
| `Verifying` | 目标实现已冻结，等待规定证据验收 | 不得新增未经重新评估的功能范围 |
| `Stable` | 约定范围已通过所需证据，可供正式依赖 | 只对已通过的范围和平台成立 |
| `Deprecated` | 不再允许新增依赖，等待迁移或移除 | 必须提供替代入口、影响面和迁移状态 |
| `Archived` | 已退出运行、编辑器、发布和现行文档入口 | 只能作为历史资料，不得恢复引用 |

`Blocked` 不是成熟度状态，而是附加结论。任何状态都可以因编译、依赖、Unity、平台、外部服务或用户决策而阻断；必须记录具体阻断证据。

## 三轴状态记录

模块状态卡必须把以下维度分开，不能用一个词同时代替三者：

| 维度 | 唯一用途 |
|---|---|
| `ModuleMaturity` | 使用本文件的 `Proposed` 至 `Archived`，描述模块演进和可依赖范围。 |
| `EvidenceLevel` | 使用 AI 交付声明 P0 的 S0-S6，描述当前声明被验证到哪一层。 |
| `DeliveryVerdict` | 使用 `Designed / Implemented-Unverified / Accepted / Released`，描述本次范围的交付结论。 |

`Blocked` 与 `Failed` 只能作为当前阻断或最近验证结果附加到状态卡，必须带证据入口。它们不改变上述三轴的语义。

## 状态权威

1. 状态必须落在当前模块已有的唯一权威开发文档、模块状态资产或项目级模块清单之一；禁止在多个 README、AIWarnings、提案和代码注释中分别维护不同状态。活跃状态卡至少记录 `ModuleMaturity`、`EvidenceLevel`、`DeliveryVerdict`、`lastVerifiedHead`、证据入口和失效条件。
2. AIWarnings 定义状态语义和禁令，不替代模块自己的实现清单；当前用户指令负责本次审计或修改授权；AICommand 只约束选中的受管执行通道，Skill 负责执行工作流。
3. 现有成熟模块不要求为了本规则一次性补齐全库状态文件。首次发生功能扩展、重构、交付或争议时，再按本规则建立或核对唯一状态入口。
4. 提案中的 `Proposed` 不能因创建空目录、空接口或占位类型自动升级。
5. 状态下降同样必须记录。例如回归失败、序列化迁移不完整或发布链断裂时，原 `Stable` 范围必须降级或标记阻断。

## 审计续接状态

模块审计续接状态的唯一固定入口是 `ES/Documentation/Status/MODULE_AUDIT_STATE.md`。用户说“审计”时默认只读；审计完成后，如果跨窗口续接确有价值，AI 最多询问一次是否记录。用户说“审计并记录”时可直接更新目标模块块；用户说“继续审计”时从该文件恢复导航。模块不明确时只询问模块范围，不再询问文件路径或区域。

可选检查点必须满足：

1. 只允许写入固定状态文件；禁止在模块文档、README、AIWarnings 或其他位置另建审计续接状态。
2. 每个模块使用稳定模块键和独立开始/结束标记；“审计并记录”只授权该模块块。
3. 写入权限只覆盖指定状态区域，不授权实现、删除、迁移、修改资产、运行 Unity、暂存、提交、推送或发布。
4. 区域必须使用稳定的开始/结束标记，更新时只替换该块；标记重复、嵌套、损坏或与他人改动重叠时停止写入并报告。
5. 检查点必须记录模块范围、成熟度、Blocked、权威入口、默认激活、依赖与消费者、半成品渗透、已有/缺失证据、Git 分支与 HEAD、相关工作树、最后动作、最小下一动作、恢复必读路径和失效条件。
6. “允许的下一写入范围”只能记录当时讨论的边界，不能向未来窗口授予权限。新窗口继续实现前仍需当前用户明确指令；只有选择受管执行通道时才要求匹配 AICommand。
7. 源码、序列化资产、配置、注册、消费者、规则、分支、HEAD、相关工作树或证据层变化后，旧检查点必须标记为 `stale`，不得直接续写实现。

下次接手流程固定为：

```text
最新 README / CurrentStatus / RuleIndex
  -> 命中的 P0 与领域专项
  -> 指定检查点与模块权威入口
  -> 当前 branch / HEAD / 相关工作树
  -> 当前源码、激活、依赖、消费者和证据复核
  -> 报告 stale 字段
  -> 在本次授权内继续
```

检查点只降低重新定位成本，不替代源码事实、Unity 运行证据或最新 AIWarnings。

完整模块审计交付后，必须按 `50_验证与发布（ValidationRelease）/AI协作治理验收（AICollaborationAcceptance）/AI协作历程与模块审计_商业可行性验收标准.md` 单独报告治理工作流的商业可行性等级。单次审计成功最多证明当前用例成立，不能直接升级为商业级。

最终答复末尾应醒目询问一次用户是否需要生成可直接交给新 AI 的交接文案。用户拒绝、忽略或本轮已经生成时不得重复询问；该文案只传递导航、证据和边界，不授予新 AI 源码修改、Git、Unity 或发布权限。

## 未开始模块

- 只登记目标、非目标、依赖、风险和进入实现的触发条件。
- 不创建大批空目录、空接口、占位程序集或无调用方的抽象层。
- 不加入 GameManager、静态初始化、资源清单、场景、Prefab、菜单或发布入口。
- 不允许现行文档、AICommand 或 Skill 把提案写成已实现能力。

## 开发中模块

- 工作区中的代码必须保持其所属程序集可编译；“还没做完”不能解释编译错误。
- 无法保持主程序集可编译时，必须缩小提交范围或放入已有实验隔离边界；不得新建无治理的程序集逃避依赖检查。
- 默认不自动注册、不默认启用、不进入正式发布；启用方式和回退方式必须显式。
- 对外 API 必须标明实验边界，稳定模块不得反向依赖未稳定实现。
- 未实现路径必须明确失败、返回不支持或被入口阻断；禁止空实现、吞异常、固定返回成功或伪造验收结果。
- 必须记录已完成范围、未完成范围、已知缺口、直接依赖、下游消费者、验证证据和下一状态的退出条件。
- 删除或中断实验模块时，必须同步移除注册、序列化引用、配置、资源、菜单、测试和文档入口。

## 状态跃迁门禁

```text
Proposed -> Scaffolded
  需要：范围、非目标、权威边界、依赖方向和最小验证方案

Scaffolded/Experimental -> Implementing
  需要：真实调用方、可编译基线、隔离或显式启用方式

Implementing -> Integrating
  需要：主路径闭环、失败/取消/退出路径、跨系统接入清单

Integrating -> Verifying
  需要：功能范围冻结、依赖审计、序列化/迁移检查、验收矩阵

Verifying -> Stable
  需要：目标范围所需的源码、Unity、测试、性能、Player 或发布证据

Stable -> Deprecated -> Archived
  需要：替代方案、消费者迁移、入口清理和残留引用扫描
```

低层证据不得冒充高层证据：源码存在不是编译通过，`.csproj` 不是 Unity 编译，Console 清洁不是 Test Runner、PlayMode、Profiler、Player、IL2CPP 或发布通过。

## 审计最小矩阵

每次判断模块状态至少回答：

| 字段 | 要求 |
|---|---|
| ModuleMaturity | 使用本规则的一个状态，并单列 `Blocked` 原因 |
| EvidenceLevel | S0-S6，精确说明平台、入口和验证范围 |
| DeliveryVerdict | `Designed / Implemented-Unverified / Accepted / Released`；不得冒充 ModuleMaturity |
| 承诺范围 | 本状态实际覆盖哪些功能、平台和入口 |
| 权威入口 | 源码、配置、资产或文档的唯一入口 |
| 默认激活 | 是否注册、自动初始化、进入场景或发布 |
| 依赖方向 | 上游依赖与下游消费者，是否发生半成品渗透 |
| 已有证据 | 精确到命令、日志、测试、场景、构建或产物 |
| 缺失证据 | 不能执行或尚未执行的验收层 |
| 退出条件 | 进入下一状态所需的最小可验证动作 |
| 续接检查点 | 是否未请求、已询问、已写入、已拒绝或已失效；精确到文件和区域 |

## 禁止事项

- 禁止用“基本完成”“差不多可用”“完成 80%”替代统一状态和范围。
- 禁止仅凭文件数量、代码量、界面可见或一次手工演示升级为 `Stable`。
- 禁止把实验模块的测试替身、Mock、Editor-only 路径写成正式运行时闭环。
- 禁止为了让状态好看而删除失败证据、跳过未实现分支或缩写阻断说明。
- 禁止机械扫描后给全项目所有目录批量写入状态；必须先确认模块边界和权威入口。
- 禁止新建第二套状态机、服务容器、事件总线或资源入口来隔离半成品；隔离不能破坏现有架构权威。
- 禁止把“审计并记录”或一次状态写入确认扩张成后续源码修改、Git 操作、Unity 操作或发布授权。
- 禁止下次 AI 仅凭旧检查点继续实现；必须先复核其 Git 基线、相关工作树和失效条件。

## 验收标准

- 模块状态、承诺范围和证据等级一致。
- 未开始模块没有伪实现和正式依赖。
- 开发中模块可识别、可隔离、可失败、可退出。
- 稳定模块没有未经批准地依赖实验模块。
- 状态跃迁存在可复现证据，缺失层明确标记为未运行或阻断。
- 可选续接检查点只写入固定文件的目标模块块，携带完整恢复入口，并能在事实漂移后明确判定为失效。
