# P2：ES Unity 菜单信息架构与入口边界

> 状态：现行架构决策，六域菜单静态迁移已完成，Unity 实机验收待完成。不得把源码扫描或生成工程编译视为 Unity 菜单已经验收。
> 最后核对：2026-08-13。

## 级别

P2——明确的编辑器规范约束。新增或修改 ES 菜单入口时必须执行；迁移完成前发现旧入口，应在不扩大业务改动的前提下同步修正引用、显示文本和测试断言。

## 统一根路径

- ES 自有 Unity 顶部菜单、`CreateAssetMenu.menuName` 与 `AddComponentMenu` 必须以精确字面量 `【ES】/` 开始；`【es】/`、`[ES]/`、`ES/`、`Window/ES/`、`Tools/ES/` 都是错误根。
- `Assets/Create/`、`Assets/`、`GameObject/` 是 Unity 宿主上下文，不是 ES 一级分类。
- 编辑器程序集能够引用公共常量时，优先使用 `MenuItemPathDefine`；运行时程序集可写稳定的 `【ES】/...` 字面量。
- 磁盘路径、类型名、协议 ID 与普通说明文字不属于菜单路径，禁止机械替换。

## 三棵菜单必须分别建模

三种 Unity 入口的用户心智不同，不得共用一套一级分类白名单：

### Unity 顶部菜单：按用户任务分类

```text
【ES】
├─ 常用窗口                 # 快捷投影，不是业务域
├─ 内容制作
├─ 项目配置
├─ 资源与发布
├─ 验证与诊断
└─ 自动化与开发
```

五个正式业务域的推荐二级树：

```text
内容制作
├─ 角色与装备
├─ 动作与轨道
├─ 图与流程
├─ 状态机
├─ 场景与对象
├─ 相机
├─ UI 与字体
├─ 音频与特效
├─ 数据表
└─ 环境

项目配置
├─ GameCore
├─ 输入
├─ 状态机
├─ 全局配置
└─ 编辑器体验

资源与发布
├─ 资源管理
├─ 收集与索引
├─ ResourcePlan
└─ 发布

验证与诊断
├─ 运行时监视
├─ 静态审计
├─ 测试与验收
├─ 验证环境
├─ 性能诊断
├─ 编辑器健康
└─ 清理与恢复

自动化与开发
├─ Agent 与协作
├─ 自动化中心
├─ AI 控制
├─ 编辑器扩展
├─ 依赖与集成
├─ 项目资产职责
├─ 文档与示例
└─ 遗留兼容
```

`内容制作/状态机`只负责状态机内容编辑；`项目配置/状态机`负责全局注册、默认值和运行参数。

### Assets/Create/【ES】：按资产类型分类

```text
Assets/Create/【ES】
├─ 内容
├─ 配置
├─ 资源管线
└─ 示例
```

`CreateAssetMenu.menuName` 自身写作 `【ES】/内容/...` 等形式；Unity 会自动放入 `Assets/Create`。显式 `MenuItem` 才使用 `Assets/Create/【ES】/...` 完整路径。

### Add Component/【ES】：按组件能力分类

```text
Add Component/【ES】
├─ 基础设施
├─ 角色与交互
├─ 相机与表现
├─ UI
├─ 资源
└─ 开发与验证
```

组件叶子允许使用对象型名称，因为 Unity 宿主已经表达“添加”；不得把顶部菜单的“内容制作、项目配置、资源与发布”机械复制到组件树。

## 常用窗口是快捷投影

- 只允许投影“打开窗口”命令，不投影写资产、修复、清理、测试执行或外部进程命令。
- 不实现第二份业务逻辑；正式业务入口与快捷入口必须调用同一个打开方法。
- 一个窗口最多一个常用入口；删除快捷入口不得影响正式入口。
- 窗口必须另有表达真实业务归属的正式入口，不能只存在于常用窗口。
- 搜索、启动器与收藏不得因两个菜单路径生成两份结果。

## 验证不等于只读

“验证与诊断”是任务领域，不构成只读、安全或无副作用承诺。

- `运行时监视`原则上只读；需要修改运行态状态的动作必须另行命名并校验执行环境。
- `静态审计`只检测。检测与修复必须拆为两个独立入口，禁止“审计”按钮静默写资产。
- `测试与验收`可能进入 PlayMode、触发编译、运行测试或生成证据。
- `验证环境`可以创建、刷新或修复测试场景与验收资产。
- `清理与恢复`明确允许有副作用，名称必须说明目标和范围，高风险动作继续遵守确认、备份与授权规则。
- 菜单分类不能替代权限、风险确认、Undo、执行环境检查或发布授权。

## 命名与排序

- 顶部菜单叶子以明确动作开头，例如“打开”“定位”“创建”“生成”“同步”“Bake”“验证”“审计”“迁移”“修复”“清理”“重置”。
- 禁止“一键处理”“工具”“执行操作”等无法判断副作用的名称。
- `Assets/Create` 与 `Add Component` 的叶子可以使用稳定对象名，不强制重复“创建”或“添加”。
- 排序按动作阶段组织：打开/定位，创建/生成，同步/Bake/应用，验证/审计/自检，迁移/修复，最后是清理/重置/删除。
- Unity `MenuItem.priority` 是全局整数，不是每个目录独立的 `0-999` 空间；应使用项目级分组基数与局部偏移，并实机验证分隔线。

## 遗留兼容

- `已废弃` 不得作为默认一级入口。
- 只有被 `ES_ENABLE_OBSOLETE_CODE` 或对应兼容程序集显式启用的入口，才允许显示在 `【ES】/自动化与开发/遗留兼容/...`。
- 迁移路径不授权恢复、修复或重新依赖废弃实现。
- 历史复盘中的旧菜单路径保留历史事实，不机械改写为新路径；现行规则、操作指南和测试断言必须更新。

## 路径不是业务身份

菜单路径只是 Unity 显示与宿主入口，不得作为跨迁移的稳定业务身份。现有启动器、命令面板、`EditorApplication.ExecuteMenuItem` 和测试若依赖路径，迁移时必须同步更新显式目录与断言；不得为了兼容保留第二套重复菜单实现。

本规则不要求在菜单迁移之前先建立新的命令总线，也不授权为所有动作新增复杂 ID 系统。若现有功能已经具有稳定命令身份，快捷投影和正式入口必须复用它。

## 迁移映射

| 旧顶部一级域 | 新位置 |
|---|---|
| `场景与对象` | `内容制作/场景与对象` |
| `运行时诊断` | `验证与诊断/运行时监视`，审计、测试、性能与清理按实际意图分流 |
| `项目设置`、顶部 `配置` | `项目配置` |
| `自动化` | `自动化与开发/自动化中心`、`Agent 与协作` 或 `AI 控制` |
| `开发与维护` | `自动化与开发/编辑器扩展`、`项目资产职责` 或 `文档与示例`；审计与诊断进入 `验证与诊断` |
| `安装与集成` | `自动化与开发/依赖与集成` |
| `示例与测试` | 验收进入 `验证与诊断`；纯教学案例进入 `自动化与开发/文档与示例` |
| `已废弃` | 仅显式兼容程序集下的 `自动化与开发/遗留兼容` |

## 正确示例

```csharp
[MenuItem("【ES】/资源与发布/资源管理/打开资源管理窗口")]
[MenuItem("【ES】/验证与诊断/静态审计/审计资源引用")]
[CreateAssetMenu(menuName = "【ES】/配置/GameCore/GameCore 配置")]
[AddComponentMenu("【ES】/资源/资源计划绑定器")]
```

## 修改后检查

至少完成以下检查：

1. 扫描所有 `MenuItem`、`CreateAssetMenu`、`AddComponentMenu`，确认根路径与各自一级白名单正确。
2. 扫描旧顶部一级域、非标准根和兼容程序集入口。
3. 同步 `EditorApplication.ExecuteMenuItem`、窗口启动器、命令面板、AICommand、Agent Skill、现行 Markdown 操作指南和测试断言。
4. 检查一个窗口是否重复出现在“常用窗口”，以及快捷入口是否误收高风险动作。
5. 在 Unity 中实机检查三棵菜单、排序、分隔线、禁用状态、快捷键与 ReloadDomain 后行为。

菜单迁移不得改动序列化字段、资源 GUID、运行时协议或磁盘目录，也不得用“规则已写入”冒充 Unity 实机验收完成。
