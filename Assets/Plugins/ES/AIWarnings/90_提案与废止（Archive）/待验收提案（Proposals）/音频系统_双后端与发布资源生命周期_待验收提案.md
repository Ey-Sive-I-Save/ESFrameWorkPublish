# ES 音频系统：双后端与发布资源生命周期待验收提案

## 提案状态

- 状态：阶段 A（Unity 后端）已开始实现，尚未完成 Unity PlayMode、Player 或 IL2CPP 验收；FMOD 与 Release Payload 仍未实施。
- 目标：在不破坏既有资源发布、AssetTable、Scope 与 ResourcePlan 约束的前提下，建立正式可用的 Unity 原生音频后端，并为 FMOD Studio 后端留出同等正式的接入路径。
- 本提案不假定项目已经安装 FMOD，也不把“能够播放一次 FMOD Event”视为完成接入。

## 结论摘要

项目现有资源系统足以承载 Unity AudioClip 的加载、预热和释放；ESAudioModule 加 UnityAudioBackend 是低风险的第一阶段。

FMOD 的难点不在 Event API，而在 .bank 文件的发布、签名校验、下载缓存、依赖闭包、Plan 持有、热更新切换和回退。目前发布协议只正式表达 AssetBundle 与代码包，不能把 Bank 伪装为 CodePackage，也不能由业务层绕过 Release Manifest 直接拼 URL 下载。

本提案采用“一个业务音频入口、两个后端、同一资源发布真相源”的方案：

~~~text
玩法 / 技能 / UI / 剧情
        |
        v
   ESAudioModule
        |
        +------------------------+
        |                        |
        v                        v
UnityAudioBackend          FmodAudioBackend
AudioClip + AudioSource    Bank + EventInstance
        |                        |
        +-----------+------------+
                    |
                    v
       ResourcePlan / Scope / 发布文件索引
                    |
                    v
          ESRuntimeReleaseDownloader
~~~

### 落地基线：模块主权与 Cue 驱动的资源计划

`ESAudioModule` 必须独立作为 `ESSystemModule`，并由 `ESGameManager.Audio` 提供唯一业务入口。`ResourcePlan`、`ESGameObjectPoolModule`、`ESRuntimeDataAsset.AudioClips`、`ESAssetScope` 与发布下载器都是它复用的基础设施，不承载音频业务本体，不对玩法暴露 Clip、Bank、Scope 或发布 Payload。

ResourcePlan 的主开发者入口必须从直接填写 `audioClips` 升级为 `audioCues`。关卡和剧情人员只选择 Cue；编辑器在烘焙时展开 Cue 的后端绑定，Unity 阶段生成既有 Clip 预热依赖，FMOD 阶段再生成 Bank 依赖：

~~~text
AudioCue
  -> ResourcePlan.audioCues
  -> Editor bake
  -> Unity: audioClips + Scope + Provider
  -> FMOD: Bank dependency + Participant + PayloadMap
~~~

`audioClips` 继续是运行时和兼容内容使用的内部资源依赖表达，不再是新内容的首选配置入口。`audioCues` 不是无意义包装：它代表一个可展开的音频语义依赖，负责把同一 Cue 的 Clip、未来 Bank 和诊断来源收敛到同一 Plan 生命周期。

## 使用流程

### 玩法、UI、技能、剧情和实体开发

业务只做三件事：在音频库选择 Cue、传递 `ESAudioCueKey`、在确有区域或剧情预热需求时把 Cue 加入既有 ResourcePlan。业务代码不直接引用 `AudioClip`、`AudioSource`、`ESAssetScope`、FMOD Event、BankKey、URL 或发布 Payload。

~~~csharp
ESGameManager.Audio.PlayOneShot(cueKey);
ESGameManager.Audio.PlayAttached(cueKey, transform);
AudioVoiceHandle voice = ESGameManager.Audio.PlayLoop(cueKey, transform);
~~~

- OneShot 不需要业务侧释放；模块在自然结束、失败、Owner 销毁、抢占或后端切换时收口 Voice。
- 只有需要提前停止、淡出或更新参数的 Loop/Music 才保存 `AudioVoiceHandle`；`Stop` 必须幂等。
- 位置、Owner、初始音量、音高和少量已声明参数通过 `ESAudioPlayRequest` 传入，不得传入底层资源对象或后端句柄。

### 内容、技能和关卡配置

1. 在 Audio Library 创建或选择 Cue，配置分类、2D/3D、变体、随机范围、冷却、并发、优先级、停止策略和后端 Binding。
2. 技能轨道、Op、UI、剧情、实体、武器、Buff 与 Shot 只保存 CueKey；现有直接 Clip 字段属于迁移期 Legacy 入口。
3. 关卡、区域和剧情 ResourcePlan 只添加 `audioCues`；编辑器烘焙出 Clip 预热依赖并显示来源、缺失 Key 和重复依赖。
4. 运行时通过现有 `PrepareAsync` / Binder / ActiveLink 生命周期准备和释放 Plan；内容人员不手工创建或释放 Scope。

### 技术音频与发布

- 技术音频维护 Cue 语义、分类路由、平台 Voice 预算、默认 3D 参数、语言变体和诊断阈值；不在业务脚本散布混音或抢占规则。
- 发布负责人只在 FMOD 阶段维护 Bank Payload、语言包和发布验收。Bank 由 Cue 展开和 ResourcePlan Participant 持有，不由关卡人员手工列举。

## 稳定性基线

以下不变量是阶段 A 的验收条件；后端、编辑器和迁移代码都不得绕过：

1. `ESGameManager.Audio` 是稳定服务对象。Provider 重建只替换内部表、后端和缓存；业务已缓存的服务引用不失效。
2. 每个 Voice 只有一个终态：自然结束、显式 Stop、Owner 销毁、并发抢占、Plan/Provider 切换或后端故障。终态处理必须幂等，并同时停止输出、释放资源持有、清空 Emitter、归还对象池和记录原因。
3. ResourcePlan 释放不能提前破坏活跃 Voice；每个 Voice 有自身可证明的 Clip/Bank 生命周期持有。反之，Emitter 回池后不得继续持有历史 Clip、Bank 或 EventInstance。
4. Cue、Clip 和 Bank 的稳定身份只经 Catalog/Manifest 解析。禁止运行时路径、GUID、裸字符串、URL 或旧 RuntimeKey fallback；失败 Cue 只记录诊断并按配置失败，不走旁路播放。
5. Provider 或后端转换必须先拒绝新请求、停止或淡出旧 Voice、等待资源边界收口、再绑定新后端。不得让旧 Clip、EventInstance、回调或异步加载结果写回新代际。
6. 并发仲裁必须可解释：全局、分类、Cue 与 Emitter 预算都有确定优先级和抢占原因；诊断能给出被拒绝、被抢占或资源失败的原因。
7. Audio 热路径只访问已解析的 Cue/RuntimeKey、预分配 Voice/Emitter 容器和固定诊断缓冲。禁止每帧反射、LINQ、字符串查表、GetComponent、临时集合或隐式加载。
8. Owner 失效、重复 Stop、迟到回调、Pool 复用和 Plan 快速反复进入/退出都必须安全；旧 `AudioVoiceHandle` 不能停止新一代同槽 Voice。
9. 用户设置、游戏存档和运行态严格分离：用户保存音量、静音、动态范围、语言和失焦偏好；游戏存档只保存可恢复 Cue 语义；底层句柄和 lease 永不持久化。
10. 诊断必须有边界：活跃 Voice 快照、失败 Cue 与抢占记录使用受限容量；关闭诊断不能改变播放结果或给正式热路径增加分配。

## 标准项目支持范围

“标准项目”指不安装 FMOD、使用现有 Unity 资源发布链仍可完成常规 3D/2D 游戏、RPG、动作技能、UI、剧情和区域环境音的正式 Unity 阶段 A。它不是以 FMOD 的高级工作流为前提，也不以“能播放 Clip”作为完成标准。

| 能力 | Unity 阶段 A 必须支持 | FMOD 阶段可增强 |
| --- | --- | --- |
| 播放形态 | OneShot、Loop、UI 2D、固定位置 3D、附着 Owner 的 3D | EventInstance、复杂路由和 FMOD 专属空间能力 |
| 音乐与环境 | Music/Ambient 单一语义入口、淡入淡出、切歌、暂停和恢复 | Timeline、Snapshot、复杂音乐状态和节拍能力 |
| 内容规则 | 变体、随机音高/音量、冷却、Cue/分类/全局并发、优先级抢占 | 参数 Label、复杂参数自动化和 FMOD-only Cue |
| 用户体验 | Master 与分类音量、静音、动态范围、语言选择、失焦策略和基础无障碍选项 | 设备、Bus/VCA 与平台原生高级控制 |
| 生命周期 | ResourcePlan 的 Cue 预热、Owner 清理、Emitter 池化、Clip 自动归还、Provider 重建收口 | Bank Participant、Sample Data、Bank 热更新和回退 |
| 诊断与验收 | 活跃 Voice、失败 Cue、抢占原因、Clip 持有、Plan 状态与内存快照 | 已加载 Bank/Payload、Bank lease、下载/校验/回退证据 |

阶段 A 的明确非目标是：自研 DSP、混音线程、空间声学、实时语音聊天、任意 URL 音频、运行中即时切换后端、多 Listener 分屏音频，以及伪造 Unity 不具备的 FMOD API。这些需求必须单独设计和验收，不能塞进“标准项目支持”导致阶段 A 失去边界。

## 必须保持的边界

- 业务运行时不得通过 AssetDatabase、资源路径、GUID 字符串回退或任意 URL 直接加载音频内容。
- Unity AudioClip 仍必须通过 ConfigKey -> AssetIdentity -> RuntimeMap -> Provider 加载；不回退到第二套资源表。
- AssetBundle 的实际引用计数仍属于 Runtime Provider。Audio Module、Plan 和 Scope 只管理自己的生命周期持有，不模拟 Bundle 引用计数。
- .bank 是独立二进制文件，不应装入 Unity AssetBundle，也不应借用 HybridCLR CodePackage 语义。
- FMOD 插件代码、原生库和平台配置属于 Player 构建内容，不允许作为运行中热更新代码替换；可热更新的是已签名、已校验的 Bank 内容。
- Player 运行中不得直接切换 Unity 或 FMOD 后端。后端变化必须走受控的停止 Voice、释放后端内容、重建后端、恢复语义状态流程。
- 常规玩法不得直接创建 ESAssetScope、AudioSource 或 FMOD EventInstance。这些只属于音频框架内部。

## 目标架构

### 1. 业务语义：AudioCue，而不是 Clip 或 Event Path

新增 ESAudioCueInfo，作为玩法唯一引用目标。Cue 具有稳定 CueKey，并保存后端无关的播放语义：

- 分类：Master、Music、Ambient、SFX、UI、Voice、Cinematic，以及项目可扩展分类。
- 优先级、最大并发数、同 Cue 冷却、抢占策略、随机变体与随机音高和音量范围。
- 2D 或 3D、距离与衰减规则、跟随目标、停止策略、暂停策略、可否虚拟化。
- Unity Binding：ESAssetReferAudioClipConfigKey 或变体列表。
- FMOD Binding：Event GUID、编辑器校验用 Event Path、必需 BankKey、参数声明与可选 Snapshot 或音乐状态绑定。

运行时 Event Path 仅用于诊断；正式运行时定位使用稳定 CueKey 和 FMOD Event GUID。业务不应把 event:/ 字符串写入技能、行为树、UI 或存档。

### 2. 唯一播放入口：ESAudioModule

ESGameManager.Audio 提供以下业务级入口：

~~~csharp
AudioVoiceHandle PlayOneShot(ESAudioCueKey cue, ESAudioPlayRequest request = default);
AudioVoiceHandle PlayAttached(ESAudioCueKey cue, Transform emitter, ESAudioPlayRequest request = default);
AudioVoiceHandle PlayLoop(ESAudioCueKey cue, Transform emitter, ESAudioPlayRequest request = default);
void Stop(AudioVoiceHandle voice, float fadeOutSeconds = 0f);
void SetParameter(AudioVoiceHandle voice, ESAudioParameterKey parameter, float value);
void SetCategoryVolume(ESAudioCategory category, float linearVolume);
~~~

AudioVoiceHandle 是无业务资源所有权的控制句柄，只可停止、淡出、设参数和查询状态。它不是 Unity Asset Handle，也不是向业务泄漏 FMOD 原生句柄的包装。

播放请求应包含位置或跟随目标、初始音量、音高、优先级修正、可取消 Token、Owner 生命周期和可选参数。音频模块负责拒绝无效 Cue、执行并发仲裁、创建或复用 Emitter，并记录结果。

### 3. 后端接口与能力声明

基础接口只承载两个后端都能正确表达的语义：

~~~csharp
interface IESAudioBackend : IDisposable
{
    ESAudioBackendCapabilities Capabilities { get; }
    UniTask PrepareAsync(ESAudioCueInfo cue, ESAudioLifetime lifetime, CancellationToken token);
    AudioVoiceHandle Play(ESAudioResolvedCue cue, ESAudioPlayRequest request);
    void Stop(AudioVoiceHandle voice, float fadeOutSeconds);
    void SetParameter(AudioVoiceHandle voice, ESAudioParameterKey parameter, float value);
    UniTask QuiesceAsync(ESAudioTransitionReason reason, CancellationToken token);
}
~~~

- UnityAudioBackend：从现有 AssetTable 获取 Clip，用池化 AudioSource 输出；按 Voice 生命周期持有 Clip，不能让播放跨越其资源持有。
- FmodAudioBackend：确保依赖 Bank 已加载后创建 EventInstance；Bank lease、事件停止、Sample Data 装载和卸载由后端管理。
- ESAudioBackendCapabilities 明确声明参数、Snapshot、Timeline、Live Update、Listener 数量等能力。核心 Cue 不依赖 FMOD 专属能力；需要 FMOD 特性的内容必须显式声明降级策略或标记 FMOD-only。

禁止为了“接口统一”而把 FMOD 的音乐时间线、Snapshot、Bus、VCA、Parameter Label 等能力压扁为 Unity 不支持的假 API。它们放在 FMOD 专属 Binding 或可选扩展中，且面板必须显示当前后端是否支持。

### 4. Emitter、Voice 与对象池

- 2D UI、非跟随 OneShot、3D 跟随、环境循环和音乐分别采用明确 Emitter 类型，不由业务随意 AddComponent AudioSource。
- Unity Emitter 使用项目对象池，但“Emitter 回池”与“资源持有释放”必须同时完成；不能因池对象仍存活而永久持有其历史 Clip。
- 每个 Voice 有确定终态：自然结束、主动 Stop、Owner 结束、被并发策略抢占、Provider 切换、后端故障。
- Loop 与 Music 必须有显式 Stop 或淡出路径；OneShot 达到结束时间或后端通知后自动归还。
- 并发控制至少支持：全局 Voice 预算、分类预算、Cue 预算、同一 Emitter 预算、按优先级抢占与不可抢占 Voice。
- 第一阶段不引入自研 DSP、混音线程或自研空间声学；Unity 和 FMOD 各自负责底层音频线程。

## 资源与发布接入

### 1. Unity 原生 AudioClip

`ESResourcePlanInfo.audioCues` 应成为内容人员配置的唯一主入口。编辑器烘焙 Cue 的 Unity Binding 后，现有 `audioClips` 与 `bakedAssets` 继续作为 Unity Clip 的内部预热入口：

~~~text
ResourcePlan.audioCues
  -> AudioCue.UnityBinding
  -> AudioClip ConfigKey
  -> ESRuntimeAssetCatalog
  -> ESAssetScope / Runtime Provider
  -> AssetBundle dependency closure
~~~

不得要求关卡人员理解、重复填写或手工同步 Cue 中的 Clip Key。当前直接 `audioClips` 列表仅保留兼容和底层实现需要；新内容经 Cue 烘焙后写入的依赖快照必须可追溯其 Cue 来源。

Plan 中预热 Clip 只表示“预期内容已准备”；真正播放的 Voice 仍必须拥有可证明的生命周期。实现可由音频模块内部的共享 lease 池完成，也可在第一阶段为每个活跃 Voice 建立受控子 Scope；无论实现方式，Voice 结束后必须归还自己的持有。

### 2. FMOD Bank 作为正式发布 Payload

扩展同一份 ESAssetReleaseBundleIndex.json，而不是建立脱离 Root Manifest 的第二份 Bank 下载清单。建议把格式版本提升，并增加通用 runtimePayloads 字段：

~~~text
PayloadKey
PayloadType                 // FmodBank；未来可扩展其他受签名运行时二进制内容
LibraryFolder / ConsumerId
DeliveryMode                // BuiltIn / Updateable / Remote
EmbeddedRelativePath
RemoteUrl
Sha256
Size
Dependencies                // 例如 Master.bank、Strings.bank、平台或语言 Bank
~~~

约束：

- PayloadKey 是稳定逻辑身份；同一发布版本中不得被不同内容重定义。
- 外部文件必须由 Root Manifest 签名链间接约束，并沿用 Downloader 的断点续传、哈希校验、缓存隔离和 LastKnownGood 回退。
- BuiltIn、Updateable、Remote 的来源约束与现有 Bundle 一致；不得让 BuiltIn 内容依赖纯 Remote 内容。
- FMOD Bank 文件必须按平台分别构建；语言 Bank 需要明确语言维度与缺失回退策略。
- Consumer 或 Library Manifest 显式声明需要的 Payload 根；下载器计算依赖闭包，不能由播放时临时猜测 URL。

下载器结果对象需携带只读 RuntimePayloadMap，并在 Consumer 或 Library 的按需下载合并时进行与 RuntimeMap 相同的冲突校验。FmodAudioBackend 只能从该 Map 获取已校验的本地路径或 StreamingAssets 定位，不能直接持有 CDN URL。

### 3. FMOD Bank 作为 Cue 的内部 ResourcePlan 依赖

不得把 `audioBanks` 暴露成关卡和剧情人员的主配置入口。FMOD 阶段由 `audioCues` 的编辑器展开结果为 Plan 生成 Bank 依赖；若实现需要内部 `audioBanks` 快照或等价数据，它只服务于烘焙、Plan Participant、诊断和发布校验，不能要求普通开发者手工维护。

Plan 服务需要增加“非 Unity 资产生命周期参与者”扩展点，例如内部 IESResourcePlanParticipant：

~~~text
Plan Context
  -> Asset Scope             (Prefab / AudioClip / SO 等 Unity 资产)
  -> Audio Bank Participant  (FMOD Bank lease)
  -> Pool Prewarm Participant
~~~

Bank Participant 必须满足现有 Plan 的 retain、取消、冷却释放、失败报告、Provider 重建和诊断规则。不得因为 Bank 不属于 UnityEngine.Object 就绕过 Plan，形成第二套匿名常驻表。

### 4. Provider 重建与热更新协议

现有资源重建会先 Quiesce Scope 或 Plan，再等待旧请求结束、释放旧 Provider、绑定新 Provider 并恢复有效 Plan。音频必须增加同等生命周期通知：

1. TransitionStarting：拒绝新播放请求；按配置停止或淡出 Voice；释放 Voice 对 Clip 或 Bank 的持有。
2. 现有 Scope、Plan、Provider 清理与重建。
3. TransitionReady：新 RuntimeMap、AssetTable 和 PayloadMap 均可用后，恢复仍被 ActiveLink、Binder 或显式生命周期持有的 Plan。
4. 音乐恢复只按 Cue 重新解析并交叉淡入；严禁保留旧 AudioClip、旧 EventInstance 或旧 Bank handle 跨过重建。

EnsureConsumerAvailableAsync 和 EnsureLibraryAvailableAsync 会下载增量内容、合并 Release 结果并重建 Provider。FMOD Payload 的按需下载必须接入同一事务，否则新 Consumer 的 Cue 可能解析成功、Bank 却未校验或没有本地文件。

## 全局音频管理面板

面板是配置、诊断和受控操作入口，不是运行中随意替换实现的开关。

| 分组 | 可作为全局设置 | 备注 |
| --- | --- | --- |
| 启动后端 | Unity 原生或 FMOD、后端编译可用性、默认降级策略 | 仅编辑器和启动期生效；Player 不允许运行中切换。 |
| 用户设置 | Master 与各分类音量、静音、动态范围、语言、耳机或扬声器预设 | 应持久化为用户设置，不写入玩法存档。输出设备受平台能力限制。 |
| 全局混音 | 分类到 Mixer Group 或 FMOD Bus 的映射、暂停和失焦策略、默认 Snapshot | 映射可全局，具体 Cue 路由不应全部硬编码在面板。 |
| Voice 预算 | 全局或分类最大 Voice、虚拟化阈值、默认抢占规则、诊断阈值 | 按平台 Profile 配置，不能只留一个桌面默认值。 |
| 3D 默认值 | Listener 策略、Doppler、全局距离曲线模板、遮挡开关与预算 | Cue 可覆盖，但必须有统一安全默认值。 |
| 资源策略 | 默认 Boot Plan、Bank 预加载策略、Sample Data 预算、切换淡出时间 | 与 ResourcePlan 和 Release Payload 联动。 |
| FMOD 专属 | Bank 加载模式、Live Update（Editor-only）、Studio Update 策略、Bus 或 VCA 映射 | 仅在 FMOD 后端已安装且可用时显示。 |
| 诊断 | 当前后端、已加载 Bank、活跃 Voice、被抢占数、失败 Cue、内存与延迟 | 必须可导出为验收证据。 |

不应作为“全局设置”的内容：某个技能的音效、某个 Boss 的参数曲线、Event Path、单个 Cue 的 Bank 归属、关卡独有环境层级。这些属于内容配置或 ResourcePlan。

编辑器中允许提供“切换后端预览”按钮，但它必须执行完整的 Quiesce -> Dispose -> Initialize -> Rebuild 流程，并明确提示预览中播放会停止。该能力不得被误实现为 Player 中的即时切换。

## 存档与用户设置：三层冻结

音频数据按以下三层保存和恢复；层间禁止混存。

| 层级 | 应保存的内容 | 禁止保存的内容 |
| --- | --- | --- |
| 用户设置 | Master 与各分类音量、各分类静音、动态范围、音频语言、失焦策略、无障碍偏好、输出设备偏好。 | 当前 Voice、AudioSource、Clip、Bank、EventInstance、Lease 与实际设备可用状态。 |
| 游戏存档 | 可恢复的音频语义，例如 MusicCueKey、MusicSectionKey、AmbientContextKey，以及玩家明确选择的电台、唱片或剧情音频状态。 | 资源 GUID、资源路径、底层播放句柄、FMOD Timeline 指针、Bank lease、随机 OneShot 和临时参数。 |
| 运行时状态 | 活跃 Voice、Emitter 池、Clip/Bank 持有、淡入淡出进度、实时参数、并发统计与 Provider 代际。 | 全部不落盘。 |

用户设置的音量保存为 dB 值，例如 -80dB 到 0dB；静音单独保存为布尔状态。取消静音时必须恢复先前 dB 值，不能把静音编码为永久覆盖音量的零值。

读档后由 ESAudioModule 依据当前版本的 Cue、Bank 与后端重新解析 MusicCueKey、MusicSectionKey、AmbientContextKey，并执行交叉淡入。第一阶段不恢复底层播放句柄、精确 Timeline 位置或旧版本资源状态。输出设备仅保存偏好，启动时必须重新检测并在不可用时回退默认设备。

## 调用点迁移

### 必须迁移

- 技能音频轨道：从直接 AudioClip 字段和 AudioSource.Play 迁移到 ESAudioCueKey 加 ESAudioModule。保留“片段退出停止”“跟随技能目标”“音量”等语义。
- OpAudio_PlayOneShot、OpAudio_SetSourcePlaying：迁移为 Cue 播放或 Loop 控制操作，不再使用 AudioSource.PlayClipAtPoint。
- UI、剧情、实体、武器、Buff、Shot 中任何新增音频调用：只允许依赖 Cue 和 Audio Module。

### 兼容期规则

- 旧 AudioClip 直接播放 API 标记为过时，但不在第一阶段删除，避免一次性破坏历史内容。
- 新内容禁止新增直接 AudioClip 播放点；编辑器检查应报告新增违规。
- 迁移完成后，旧入口仅保留显式 Legacy 命名或彻底删除，不能继续作为“方便的旁路”。

## 分阶段实施

### 实施节奏与验收前提

AI 可以显著压缩模块骨架、Cue、调用点迁移、编辑器、下载协议与自动化测试的编码时间，但不能替代 Unity 域重载、Player 构建、IL2CPP、FMOD Bank 制作、原生库装配、真机性能和真实热更新回退验证。下表的“含真实验证”才是可对外讨论的实施预估：

| 范围 | AI 编码预估 | 含真实验证的预估 |
| --- | ---: | ---: |
| 最小原型 | 0.5-1 天 | 1-2 天 |
| 阶段 A：Unity 正式版 | 3-5 天 | 5-8 天 |
| 阶段 B：Release Payload | 3-5 天 | 5-8 天 |
| 阶段 C：FMOD 与 IL2CPP | 4-8 天 | 8-15 天 |
| 双后端正式版本 | 10-19 天 | 18-33 天 |

这些预估的前提是：工程先达到真实 `0 error`；Unity 可持续刷新工程并编译；FMOD 包和目标平台原生库已经准备；能够执行真实 Player、IL2CPP、网络下载和回退验收。任一前提不成立时，阻断时间必须单独记录，不能算作“AI 编码已完成”。

当前最合理的目标是先以 5-8 天完成可验收的 Unity 阶段 A。阶段 A 未达成真实验收前，不把 FMOD 和 Release Payload 协议混入实现，以免资源生命周期、后端问题与发布协议问题互相遮蔽。

### 阶段 A：统一语义与 Unity 后端

1. 定义 ESAudioCueInfo、CueKey、分类、播放请求、VoiceHandle 与基础诊断模型。
2. 实现 ESAudioModule、UnityAudioBackend、池化 Emitter 和生命周期收口。
3. 在 ResourcePlan 增加 Cue 主入口，并将其 Unity Binding 烘焙为现有 AssetTable、Scope、ResourcePlan 的 Clip 依赖；不改 Release 协议。
4. 迁移技能轨道与 Audio Operation，并加入直接播放的静态检查。
5. 实现全局面板中的用户音量、分类路由、Voice 预算和运行时监视。

阶段 A 的完成标准是：不安装 FMOD 时，项目已有资源系统可支撑正式 Unity 原生音频工作流。

### 阶段 B：发布 Payload 基础设施

1. 扩展 Publisher、Root、Consumer、Library Manifest 和 ESAssetReleaseBundleIndex.json，引入受签名 runtimePayloads。
2. 在 Downloader 实现 Payload 依赖闭包、续传、校验、缓存、LocalBuild、HotUpdate 与 LastKnownGood。
3. 将 PayloadMap 加入下载结果合并、增量 Consumer 或 Library 激活与诊断。
4. 为 Provider 重建增加框架级生命周期参与者，避免 Audio 依赖隐式执行顺序。

阶段 B 不安装 FMOD 也必须独立验收，因为它是通用发布协议变化。

### 阶段 C：FMOD 后端

1. 建立 FMOD 插件安装、平台原生库、Scripting Define Symbol、Player 构建校验。
2. 实现 BankProvider、Bank lease、EventInstance Voice、参数、Bus、Snapshot、3D Listener 与 Bank 卸载协议。
3. 将 Cue 展开的 Bank 依赖接入 ResourcePlan Participant，并完成 Provider 重建恢复；不新增面向普通开发者的直接 Bank 配置入口。
4. 为 Cue 配置 Unity 或 FMOD Binding、能力提示和内容校验。
5. 在目标 IL2CPP 平台实际验证 Bank 热更新、回退、语言切换、内存和压力场景。

## 验收矩阵

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| P1 | Unity OneShot | Cue 播放、自然结束、Emitter 回池、Clip 持有归还；无历史 Clip 常驻。 |
| P2 | Unity Loop 或 Owner 销毁 | Owner 或显式 Stop 触发淡出与释放；重复 Stop 幂等。 |
| P3 | Clip ResourcePlan | Plan 预热后播放无重复加载；Plan 释放不提前破坏仍在播放且独立持有的 Voice。 |
| P4 | Voice 并发 | 触发 Cue、分类、全局预算时，抢占顺序与诊断记录符合配置。 |
| P5 | Provider 重建 | 切换开始后无新 Voice 进入旧后端；无旧回调或旧 Clip 写回新 Provider。 |
| P6 | ActiveLink 或 Binder 恢复 | 有效 Plan 在 Provider 重建后恢复；音频只重新解析当前版本资源。 |
| P7 | Unity LocalBuild 或 HotUpdate | AudioClip 在内置、更新、远端分发模式均按既有 AB 协议加载。 |
| P8 | Payload 校验 | FMOD Bank 的缺失、Hash 不符、依赖环、非法路径、错误 DeliveryMode 必须阻断激活。 |
| P9 | FMOD Bank 生命周期 | Bank 在最后 lease 归还且关联 Event 已结束后卸载；不得早卸或永久常驻。 |
| P10 | FMOD 增量 Consumer | 按需 Consumer 下载后，Cue、Bank Payload、Catalog 与 Provider 同一事务可用。 |
| P11 | HotUpdate 回退 | 新发布初始化在 Bank 或 AB 校验失败时，不提交 LastKnownGood；离线回退可启动最近成功版本。 |
| P12 | IL2CPP Player 压测 | 目标平台下验证 3D Voice、Bank、切换、内存、无 Native 崩溃与无未观察异常。 |

每个场景至少记录：发布版本、后端、平台、CueKey 或 BankKey、Voice 状态、Plan RetainCount、已加载 Bank 或 Payload、失败原因、内存采样和 Unity Console 输出。P5、P8、P10-P12 不得仅以 Editor Mock 代替真实 Player 证据。

## 风险与待决项

| 问题 | 建议结论 | 需要评审确认 |
| --- | --- | --- |
| 是否立即接 FMOD | 不立即。先完成阶段 A，确认项目内容、混音与性能需求是否超过 Unity 后端能力。 | 目标品质、平台、音频团队工作流。 |
| Release Payload 放在何处 | 扩展同一 ESAssetReleaseBundleIndex.json，保持运行时物理文件唯一真相源。 | 字段命名与协议版本迁移方案。 |
| Cue 的数据归属 | 根 Cue 或 Bank 配置是 GameCore；单个播放请求只保存 CueKey 与运行时参数。 | 是否需要独立 Cue AssetTable，或先以 GameCore 注册表实现。 |
| Bank 预加载粒度 | 以 Content、Region、剧情阶段的 Cue 驱动 ResourcePlan 为主，不按单次播放临时下载或手工 Bank 配置。 | 首包预算、场景切换预算、语言资源策略。 |
| 音乐恢复 | Provider 重建后按 Cue 重播并交叉淡入，不尝试持久化底层播放位置作为第一阶段保证。 | 是否需要音乐时间线或节拍级恢复。 |
| 网络与多人同步 | 网络同步 CueKey、时序和参数，不同步后端句柄或 Event Path。 | 现有网络权威与延迟补偿方案。 |

## 明确不属于本提案

- 用单个 AudioManager MonoBehaviour 替代 GameManager Module、ResourcePlan 或发布系统。
- 让业务直接下载 .bank、直接调用 FMOD API，或在技能中保存 CDN 地址。
- 重写现有 AssetBundle Loader、对象池或全局引用计数。
- 自研 DSP、混音引擎、空间声学求解器或自研音频线程。
- 宣称 FMOD 自动带来 3A 音频品质。FMOD 提供工作流和能力上限，内容制作、混音、预算、验证与平台调优仍是项目责任。

## 最终准入标准

阶段 A 的 P1-P7 必须在 Editor PlayMode 与至少一个 IL2CPP Player 中通过，才允许将 Unity 后端标记为可用。

阶段 B 的发布协议变更必须完成真实 LocalBuild、HotUpdate、增量 Consumer、断网回退和错误文件校验，才允许发布包含外部 Payload 的版本。

阶段 C 的 P8-P12 必须在每个计划支持 FMOD 的目标平台实跑通过；任一出现未校验 Bank、旧后端 Voice 跨 Provider 存活、Bank lease 残留、非法路径下载、Native 崩溃或 IL2CPP 构建缺库，则 FMOD 后端不得标记为正式可用。
