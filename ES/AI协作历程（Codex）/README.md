# ES AI 协作历程

本文件夹用于保存 ESFramework 与 Codex 每个真实对话窗口的逐任务协作历程，包括决策演进、实际动作、验证证据、失败纠正和未完成事项。

## 文件夹边界

- 这里记录“我们做过什么、为什么这样做、当时达到什么状态”。
- 这里不是正式架构规范，不替代 `Assets/Plugins/ES/AIWarnings`。
- 源码、Unity 实际运行结果和正式 AIWarnings 与本文件夹内容冲突时，以源码和最新验收证据为准。
- **一个真实对话窗口严格对应一个文件。** 不按主题拆分，同一窗口讨论的全部主题都写入该窗口自己的同一文件。
- **禁止为同一窗口按主题另建文件。** 编辑器、资源、运行时、AIWarnings 等内容必须保留在同一窗口文件的时间线中；主题索引只能作为时间线之后的检索辅助。
- 只有用户明确要求为新对话窗口创建或维护历程时，才新建该窗口文件；未获授权不得自动建档。获授权后不能续写、覆盖或合并到其他窗口的文件，同一窗口后续更新只能维护自己的文件。
- 每个窗口自行决定自己的文件标题，不使用目录统一分配的主题标题。
- 文件名强制使用 `yyyy-MM-dd_HHmmss_<具体职责大纲简述>.md`；时间戳记录建档时间，后半段必须回答“这个 AI 在该窗口具体做了什么”。
- 职责大纲使用 2 至 4 个“职责动作 + 对象”短语并以下划线分隔，例如 `编辑器工具重构_资源规则编写_GameCore配置收口`。
- 文件名必须至少出现一个明确职责动作，推荐使用 `实现`、`重构`、`修复`、`编写`、`审查`、`复核`、`验证`、`诊断`、`迁移`、`收口`、`治理`；只列 `GameCore`、`资源`、`音频`、`相机` 等领域名不合格。
- 职责用词必须与时间线中的实际动作一致：只做审查不得写“实现”，只转述用户报告不得写“验证”，只讨论方案不得写“落地”。
- 禁止只用 `合作历程`、`协作续篇`、`实际工作记录`、`阶段总结` 等通用词作为大纲；禁止把 `已完成`、`已通过` 等可能过期的状态写入文件名。
- 文件名大纲不要求与正文标题相同：标题由窗口自由决定，文件名负责稳定说明职责与内容范围。
- 同一窗口后续工作导致原大纲明显失真时，应重命名自己的文件并同步本 README；必须保留最初建档时间戳。
- 正文必须另外标注各项功能的大概实现日期，不能用建档或复核日期冒充实现日期。
- 实现日期应说明依据；无法确认时写“日期待核”，不得猜测。
- 正文主体必须是按接受顺序排列的任务时间线，尽量覆盖该窗口接受的所有用户任务；不得只写领域总结、最终成果或自我职责概括。
- 每条任务至少记录：顺序或大概时间、用户交付/要求、窗口当时接受的范围、实际动作、修改或检查对象、验证证据、当时结论与剩余项。
- 用户只提供背景而未要求当前窗口处理的内容，标为“前置上下文”，不得冒充本窗口接受的任务；其他窗口完成的实现只能作为“外部交付复核”记录。
- 任务中途被用户纠正、范围改变、执行失败、误改其他窗口文件或撤回结论时，必须按发生顺序保留，不得只留下修正后的漂亮结果。
- 分类摘要、最终结论和未完成清单可以保留，但只能放在完整任务时间线之后，不能替代时间线。

## 详尽性硬要求

本节只在用户已经明确授权创建、更新、恢复或补全历程后生效。它约束“获准写入时如何保证质量”，不授予 AI 自动写入权限。历程的首要目标是让后续 AI 能从文件中尽量还原授权范围内的实际工作，而不是追求篇幅短或阅读漂亮。

1. **独立请求原则上一对一记录。** 用户每次提出新的验收对象、API 语义、设计决策、错误、性能问题、实现要求或规则修订，都应成为独立任务节点。
2. **追问改变语义时必须拆条。** 例如“能否释放”“是否计数”“能否提前取消”“是否需要独立 Lease”属于不同决策，不能合并成“讨论资源生命周期”。
3. **长窗口不设条数上限。** 实际接受约 30 个任务，就应保留接近 30 个或更多任务节点；禁止为了简洁压缩成 5 至 10 个主题。短窗口也不为凑数量虚构任务。
4. **每条不能只写结果。** 至少说明用户要求、接受范围、实际动作或分析、关键证据、当时结论、未完成项；没有执行工具时明确写“仅基于用户报告或设计讨论”。
5. **实现、复核和讨论严格分栏。** 其他窗口提交的源码只能记录为外部交付及本窗口复核；不得把“我认同”“我检查过”改写成“我实现了”。
6. **失败和反复属于正式时间线。** 错误判断、过严或过松的 API 结论、补丁失败、跨窗口误写、用户否决及后续撤回都必须保留。
7. **上下文压缩后仍要尽力恢复。** 应结合当前对话、压缩摘要、已有工具证据和先前历程重建任务；无法确定的细节标记“待核”，不能直接省略整段历史。
8. **交付前执行覆盖审计。** 对照可见用户消息统计可操作请求、时间线节点和排除项；明显少于实际请求数时必须继续补写。被排除的消息需说明是纯背景、重复确认还是未被当前窗口接受。
9. **按时间线优先，主题索引次之。** 可以增加领域索引帮助检索，但不得把任务重新移动成彼此割裂的主题文档或破坏原始顺序。
10. **状态随当时证据记录。** 后续修复不能抹掉早期“未完成”结论，应新增后续任务说明状态如何变化，以保留决策演进。

## 历程执行门禁

本节首先约束写入授权，其次才约束获准写入后的完整性。业务回答、源码检查、实现和验证不得因为历程未更新而被阻断。

### G1：用户授权优先

- 只有用户明确提出“创建、更新、补全、恢复、整理或交接历程”等要求时，AI 才能写入 `ES/AI协作历程（Codex）`。
- 普通问答、代码修改、工具读取、构建、测试、用户纠正或结论变化都不自动授予历程写入权限。
- 距上次历程更新、用户拒绝或询问起经过大约 10 轮有实质内容的对话后，AI 可以简短询问一次是否需要整理历程；用户明确同意前仍不得修改任何历程文件。
- 用户拒绝、忽略或要求稍后再说时，继续业务任务，不得催促、反复询问或把历程维护置于业务工作之前；再次询问至少再等待约 10 轮。
- 用户授权只覆盖其明确指定的窗口、时间范围和操作；不得借一次授权恢复长期自动写入。

### G2：修改前确认唯一档案

获准维护历程后，在开始修改历程文件前，必须使用 `窗口档案ID` 定位本窗口唯一职责文件，并核对至少两个尾部任务与授权范围连续。归属不唯一时：

1. 停止写入任何已有窗口档案；
2. 在当前任务状态中标记“待归属确认”；
3. 按下方“Codex session 定位与失联窗口恢复”执行只读匹配；
4. 仍无法唯一确认时新建独立恢复档案或请求用户确认，禁止试写和事后撤回。

### G3：授权范围内统一整理

用户授权更新后，AI 可以一次性整理授权范围内的任务、工具证据、修改、构建、失败、纠正、撤回和剩余项，不要求每个动作发生后即时写盘。每个实际新增节点至少包含：用户要求、接受范围、实际动作、修改或检查对象、证据、当时结论、剩余项。仅写“已处理”“已完成”或主题摘要判定为未落账。

### G4：完成前覆盖审计

只有在用户授权历程维护，且 AI 准备宣称“历程已更新、已补全或已恢复”时，才必须产出并核对以下审计数据：

```text
可见用户消息数 = 独立任务数 + 补充/纠正数 + 排除消息数
应记录节点数 = 独立任务数 + 补充/纠正数
实际新增或恢复节点数 = 本轮对应时间线节点数
```

- `实际节点数 < 应记录节点数` 时禁止宣称完成，必须继续补写。
- 多条消息共享一个执行轮或最终答复时仍按语义计数；允许共享证据，但不得吞掉节点。
- 排除消息必须逐条说明属于纯背景、完全重复确认、系统/开发者注入或未被当前窗口接受的请求；禁止用“其他”批量排除。
- 对历史恢复任务，还必须核对原 session 的用户消息数、任务开始/完成/中止数与恢复节点数，并解释数量差异。

### G5：机械校验

完成一次获授权的历程写入前必须检查并报告：

1. `T` 编号连续且尾号与 README 索引一致；
2. 每个获授权新增的节点具备 G3 要求的字段，缺失项有明确原因；
3. 当前窗口仅认领一个文件，窗口档案ID 全目录唯一；
4. 文件名职责动作与正文实际动作一致，不把讨论、转述或复核写成实现；
5. README 链接存在，文件严格 UTF-8、无 U+FFFD、无尾随空白；
6. 已跟踪文件执行 `git diff --check`，未跟踪文件执行等价的新增文件空白检查。

任一项失败时，历程状态只能写“未完成”或“待修复”，不得先给完成结论再等待用户指出缺口。

## 授权维护与认领

AI 只有在用户明确授权后才执行以下闭环：

```text
接收用户的历程维护授权
  -> 用窗口档案ID定位自己的文件
  -> 核对文件尾部任务与授权范围连续
  -> 整理用户授权覆盖的任务与证据
  -> 追加或恢复完整任务节点
  -> 更新尾部任务号与状态
  -> 职责范围明显变化时审计并重命名文件
  -> 更新本 README 的ID索引和链接
```

补充约束：

1. 用户首次授权当前窗口建档时生成永久 `窗口档案ID`，格式为 `ES-CODEX-yyyyMMdd-HHmmss`；重命名不改变 ID。
2. 档案头部、上下文恢复和交接摘要必须给出 ID 与当前绝对路径。
3. 每次获授权维护前按 ID 查索引并核对至少两个尾部节点；不能唯一确认时执行 G2，不得试写。
4. 禁止自动追加独立任务；中止、失败、纠正和文件职责变化只在用户授权范围内整理。

## Codex session 定位与失联窗口恢复

当用户明确要求恢复失联窗口，且原对话已经达到上下文上限、持续容量失败、无法继续维护自己的档案，或上下文压缩后遗失 `窗口档案ID` 且不能靠文件尾部唯一认领时，允许从本机 Codex 历史记录恢复。该机制只用于获授权的兜底恢复，不授予日常自动维护权限。

### 第一步：模糊定位 session 路径

优先运行 [`Tools/Find-CodexSession.ps1`](Tools/Find-CodexSession.ps1)，从全局 `history.jsonl` 按 session ID、主题词、原提示片段、日期和项目 CWD 搜索候选，并返回类似以下绝对路径：

`C:\Users\asus\.codex\sessions\2026\07\23\rollout-2026-07-23T15-16-39-019f8dd5-6319-7fb3-a5fe-8136852d041e.jsonl`

```powershell
# 多关键词模糊定位
& '.\ES\AI协作历程（Codex）\Tools\Find-CodexSession.ps1' `
  -Query 'ResourcePlan TemporaryScope Raw AliyunOss' -Top 5

# 日期与项目路径缩小范围
& '.\ES\AI协作历程（Codex）\Tools\Find-CodexSession.ps1' `
  -Query '资源加载方案 UniTask' `
  -ProjectPath 'F:\aaProject\ESFrameWorkPublish' `
  -Since '2026-07-20' -Until '2026-07-31 23:59:59'

# 已知 session ID 时精确定位
& '.\ES\AI协作历程（Codex）\Tools\Find-CodexSession.ps1' `
  -Query '019f8dd5-6319-7fb3-a5fe-8136852d041e'
```

定位分数只用于候选排序：`ExactSessionId` 为精确 ID，`HighCandidate` 为高相似候选，`ManualReview` 必须人工比较，`LowCandidate` 需要增加关键词或时间条件后重搜。低分候选不得直接作为恢复源。默认只返回本机文件仍存在的候选；诊断已丢失记录时才显式使用 `-IncludeMissingFiles`。搜索结果中的 `UserMessages` 来自 `history.jsonl`，只用于辨认规模；完整覆盖数量必须在选定 session JSONL 中重新统计。

### 数据源与只读边界

1. 先用 `%USERPROFILE%\.codex\history.jsonl` 查找候选会话、用户提示和时间范围，再以 `%USERPROFILE%\.codex\sessions\yyyy\MM\dd\rollout-*.jsonl` 作为逐轮恢复的主要证据。
2. 必须逐行使用结构化 JSON 解析，例如 PowerShell `ConvertFrom-Json`；禁止仅靠 `Select-String`、正则截取或肉眼拼接推断任务边界。
3. `.codex` 内部 JSONL 是本机已观察到的实现格式，不视为稳定公开 API。恢复前先探测当前文件的顶层 `type`、`payload.type` 和字段存在性；未知记录保留计数并标为无法解释，不得硬套旧结构。
4. session 与 history 文件全程只读，禁止修改、格式化、截断、移动或删除。若会话仍在写入，使用允许共享读取的快照，记录读取前后文件大小、最后修改时间和最后事件时间；大小变化时重新取最终快照或明确标注恢复截止点。
5. 系统提示、开发者提示、环境注入、权限说明和 world state 不属于用户任务，不写进业务历程。凭据、Cookie、Authorization、API Key、环境密钥、个人隐私及无关的大段工具输出必须脱敏或省略。
6. 路径确认后，长会话优先复用 [`Tools/Recover-CodexSessionHistory.ps1`](Tools/Recover-CodexSessionHistory.ps1) 进行结构化恢复；使用前仍需人工确认档案归属、标题、职责大纲和档案 ID，生成后必须抽查节点语义与执行本 README 的覆盖门禁。两个脚本都是辅助工具，不是自动认领或自动签收器。

### 逐轮重建

按 `turn_id`、时间戳和文本联合去重用户消息，并尽量恢复以下事件关系：

```text
task_started
  -> user_message / 同轮补充消息
  -> commentary
  -> tool call / tool output
  -> final_answer
  -> task_complete

turn_aborted
  -> 明确保留为中止，不得推断为已完成
```

- 一轮含多条用户消息时，若后消息是独立语义要求，时间线仍拆成独立节点，但记录它们共享同一执行轮和最终答复。
- 工具调用只摘要与任务有关的读取、写入、构建和验证证据；不得把读取源码写成修改源码，也不得把回答建议写成已经实现。
- `task_complete` 缺失、`turn_aborted`、工具失败、未返回最终答复和未验证结论都必须原样保留。
- 恢复文件必须写明来源路径、Codex session ID、会话开始时间、工作目录、快照大小与时间、用户消息/完成/中止/工具数量、解析错误数和恢复日期。

### 第二步：确认窗口档案归属

session 路径确认后，再用精确 session ID、会话开始时间、CWD/项目路径、首尾用户提示、长提示前缀和既有时间线尾部判断它应写入哪个窗口档案。不得把第一步的搜索分数直接当作档案所有权，也不得只按文件名主题或最近修改时间认领。

| 档案归属证据 | 处理 |
|---|---|
| 已有档案精确记录相同 session ID | 核对档案尾部连续性后可在原文件恢复 |
| 无精确 ID，但开始时间、CWD、首尾任务和尾部时间线唯一吻合 | 人工确认后可在原文件恢复，并补写 session ID |
| 多个档案都可能匹配或任一关键证据冲突 | 不写任何已有档案 |
| session 已确定，但没有可靠已有档案 | 新建独立恢复档案并分配永久窗口档案ID |

session 本身尚未确定时继续搜索或请求用户确认；只有 session 已确定而档案归属不明时，才允许新建恢复档案。恢复完成后加入 ID 索引；以后发现更强归属证据时，只能保留来源和迁移说明后人工治理，禁止静默合并或删除证据。

## 使用顺序

1. 先读 `Assets/Plugins/ES/AIWarnings/00_开始阅读（Start）/当前状态（CurrentStatus）.md`。
2. 再按 `规则索引（RuleIndex）.md` 进入当前任务的现行规则。
3. 最后按本 README 的“当前历程”与“历史快照”阅读协作背景。

历程中的“未完成”“当前阻断”只表示对应记录时间点的事实；后续规则或验收已经变化时，以最新 AIWarnings、源码和实际运行证据覆盖。不得依据旧历程恢复已废止 API、配置或架构方向。

## 状态标记

- `已落地`：源码或文档中已经存在，但仍可能缺少 Unity/Player 验证。
- `已分析`：完成了判断或方案，尚未代表代码已经实现。
- `联调中`：代码链路存在，缺少完整运行、发布或网络证据。
- `未完成`：明确仍有代码、测试或外部环境工作。
