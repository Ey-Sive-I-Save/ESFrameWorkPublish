# TaskContextRuntime v1 API Contract Matrix

| API | Owner | Inputs | Output | Mutation | Failure boundary |
|---|---|---|---|---|---|
| `New-ESGoalRevision` | platform | goal identity, scope, acceptance intent, budget, optional parent | immutable frozen GoalRevision | create-only GoalRevision | duplicate identity with different content, invalid type, empty/duplicate scope |
| `Resolve-ESGoalRevision` | platform verifier | project-relative GoalRevision path | canonical identity and revision hash binding | none | malformed UTF-8/JSON, extra field, non-frozen state, forged hash |
| `New-ESTaskContextTask` | platform | task identity, immutable RoutePlan path, compatibility PlanHash equal to the recomputed routePlanHash, frozen GoalRevision, frozen AcceptanceProfile with claim-to-verifier and central Evidence contract bindings, requested sourceScope | `Active+Live` revision 1 with immutable RoutePlan identity/artifact/snapshot, GoalRevision path/hash, and Evidence contract ID/hash bindings | create-only first event | duplicate TaskId, unsafe path, forged RoutePlan, stale snapshot, unregistered stage/Profile/route/depth relation, Goal mismatch, unknown verifier, or missing Evidence contract |
| `Confirm-ESTaskSourceScope` | platform | current CAS pair | verified paths and SHA-256 binding | one event | missing/drifting/escaping source, CAS conflict |
| `Submit-ESTaskEvidenceSet` | platform | canonical central-contract CandidateEvidence or explicit legacy v1 compatibility input, artifact manifest, and current CAS pair | central-contract EvidenceSet with derived outcome, artifact hash, verifier identity, input mode, and preserved candidate fields | one event | contract/hash drift, added authority fields, missing fields, duplicate claims, stale source binding, malformed evidence, candidate/hash/outcome contradiction |
| `New-ESTaskEvaluationRecord` | platform evaluator | task identity, frozen evaluator/profile, current CAS pair, idempotency key | immutable task-object EvaluationRecord | create-only evaluation record; lifecycle revisions and statuses unchanged | stale CAS, evaluator/schema drift, record identity/hash mismatch, scope expansion |
| `Get-ESTaskCommercialObservation` | TaskContextRuntime read model | one TaskId and verified event/evaluation store | immutable in-memory task-object observation with source snapshot hash | read-only; no lifecycle or report write | event/Receipt/EvaluationRecord tamper, contract drift, task/scope mismatch |
| `Complete-ESTaskContextTask` | platform | current CAS pair | accepted/rejected/undetermined decision | one event and, only for accepted, one immutable Receipt | missing/freshness/contradiction/source/artifact/GoalRevision drift gates |
| `Set-ESTaskDeliveryAcceptance` | delivery adapter or user-facing host | accepted/rejected and current CAS pair | final delivery state only | one event | task is not accepted `Completed+Frozen`, delivery is not pending |
| `Invoke-ESTaskContextTransition` | platform adapters | named transition and current CAS pair | next legal lifecycle state | one event | illegal transition or CAS conflict |
| `Get-ESTaskContextState` | any read adapter | task identity | latest state | none | missing or invalid event chain |
| `Test-ESTaskContextIntegrity` | verifier | task identity | integrity result and orphan count | none | hash, gap, transition, or Receipt binding mismatch |

`Test-ESPlatformEvidenceContract.ps1` validates canonical input, the legacy compatibility projection, normalized output, forged bindings, unsupported fields, missing fields, and contract drift. `Test-ESTaskContextRuntimeSchema.ps1` validates platform-generated representative events and Completion Receipts while resolving normalized EvidenceSet through the external central schema. `ESJsonSchemaLite.psm1` rejects any schema keyword outside its implemented Draft 2020-12 subset so future schema growth cannot silently bypass validation.

`Test-ESEvidenceVerifierRegistry.ps1` independently validates registry shape and semantics. It proves that bound definition drift limits only the current completion claim while an unrelated valid registry addition does not invalidate the unchanged verifier selected by an existing task. It also exercises `platform.static-replay-v1`: the verifier binds the shared runner implementation hash, refuses sourceScope expansion before execution, reruns StaticDeepReplay in a bounded scratch path, rejects producer outcome forgery, and emits a platform-derived regression `OutcomeAssertion` without retaining scratch state.

Stable identity is `TaskId`; goal identity is the immutable `goalId + goalRevision + revisionHash` tuple. Every mutation requires `ExpectedTaskRevision`, `ExpectedContextVersion`, and `IdempotencyKey`. Each key is bound to the canonical operation fingerprint, so only an exact retry can return the original event state. The event log and receipts are create-only. `ESAutomationRunStatus.Accepted` is not a compatible value for `completionDecision`.

Canonical `candidateOutcome`, `candidateEvidenceHash`, and `candidateProducerType`, plus their legacy `outcome`, `evidenceHash`, and `producerType` aliases, are never authoritative. The frozen AcceptanceProfile binds the central Evidence contract ID/raw SHA-256 and must explicitly select one registered verifier for every required claim; there is no guessed default. Each verifier declares the claim IDs it is qualified to prove, and the profile binds both the registry snapshot hash and each selected verifier definition hash. `platform.file-hash-manifest-v1` is restricted to `source-integrity...` claims: it rereads each bounded project file, recomputes SHA-256, and derives `passed`, `failed`, or `unverified`. `platform.static-replay-v1` is restricted to `regression...` claims: it validates a minimal request artifact, preflights every declared source against the frozen task sourceScope and verifier budget, checks the registered runner hash, reruns the shared validator, and derives the authoritative outcome and evidence hash from the replay result. Neither verifier can prove Unity Runtime, release, visual, performance, or arbitrary business claims. The submitted producer label is retained only as `candidateProducerType`, while normalized evidence records platform verification authority. Missing bindings, contract drift, claim/verifier mismatch, or selected-definition drift cannot produce accepted completion. Unrelated registry entries do not change the bound verifier definition.

Adapters may translate Automation Run, Codex Session, ReadSnapshot, Semantic Archive, Skill, or Worker data into these inputs. They may not bypass the platform evaluator or mutate event files.

`ES/Automation/RoutePlan/ESRoutePlanContract.psm1` is the single PowerShell implementation for RoutePlan canonical JSON, routePlanHash/routePlanId, SourceRefsHash, current artifact rereads, Git HEAD, registry membership, and depth authorization. `Test-ESRoutePlanContract.ps1`, TaskContext fixtures, and `ESTaskContextRuntime.psm1` consume this module rather than maintaining independent field lists.

`es.task-context.evaluate@1` is the only source-registered managed adapter in v1. It binds the existing `task.context-runtime.mutate` command, a fixed TaskContract, one PowerShell Worker hash, one input Schema hash, and the `New-ESTaskEvaluationRecord` platform API. Automation run status and CompletionDecision are not accepted as evaluation inputs, the Worker output directory is fixed to `ES/Automation/Runs/TaskContextEvaluation/<runId>`, and registration failure is isolated from unrelated Automation endpoints. These are source/static properties; Unity-hosted registration and production execution remain unverified.

Adapter availability is governed separately from the platform API. The Core v1 API is statically acceptable without AIBrain `runTask`, an `ESAutomationFacade` business endpoint, Worker EvidenceSet submission, Codex Session or Semantic Archive adapters, or Unity Editor task creation. These integrations are required only when the active Runtime/Release profile explicitly selects their stable capability IDs from `es-task-context-runtime-integration-policy-v1.json`. No adapter may acquire lifecycle ownership, and capability discovery alone never means execution availability.
