# ES Framework Publish 静态文档阅读器标准

## 定位

本标准约束 `ES/Documentation/StaticSite/ESFrameworkPublish_技术文档.html` 的信息架构、版式和交互。它服务于维护者连续阅读复杂工程知识，而不是把单文件 HTML 做成仪表盘、产品落地页或源码仓库浏览器。

更新该 HTML 的 AI 或开发者必须先读取本文件、`DOCUMENT_SYNC.md`、`DOCUMENT_SYNC.json` 和 `DOCUMENT_LOCAL_UPDATE_LEDGER.md/.json`。涉及源码行为时，仍必须遵守同步记录中的源码审阅流程；本标准不能替代语义分析。

## 不可妥协的阅读结构

1. 桌面以“左目录 + 聚焦正文阅读列”为默认结构。解释性段落保持在易读行长；承载流程、矩阵和对照表的正文工作区可扩展至 `900px` 至 `1040px`，不得为了窄列强迫多列表格横向滚动。
2. 左目录仅承担章节定位。分组可以折叠，但项目编号、统计数字和状态标签不能成为视觉主体。
3. 页面首屏先交代当前主题、阅读范围和入口链接；代码规模、矩阵、流程和表格必须在读者理解主题后出现。
4. 每个大章节只服务一个主题。跨主题的对比、验收和源码证据应作为该主题的组成部分，而不是单独堆出控制台式小组件。
5. 手机端默认先显示正文。目录必须通过顶栏菜单按需展开，不能把读者推过一整屏导航后才看到标题。
6. 仅在超宽屏允许右侧来源栏。它必须提供实际源码或规范入口树，随窄屏消失；禁止用静态状态、统计或重复说明填充第三栏。

## 视觉与排版规则

- 默认深色主题。以接近黑色的低饱和底色、柔和文本对比和细分隔线建立层级；浅色仅作为用户可选主题。
- 不复制任何第三方产品的品牌、图标、源码、插画或 CSS。可以借鉴通用的文档阅读原则：窄正文、克制侧栏、明确标题层级、源码链接紧贴解释。
- 标题通过字号、留白和分隔线建立层级，不依赖大色块、渐变、装饰球或营销式 Hero。
- 正文段落优先于卡片。只有比较矩阵、流程状态或重复的独立工作项可以使用有边界的容器；不得把页面章节包进卡片，也不得嵌套卡片。
- 表格用于横向比较，流程图用于顺序关系。两者必须给出结论性文字，不能用布局替代解释。
- 源码路径、原始规范和可折叠源码属于证据层，应比解释正文更轻。它们不能被用作增加“文档内容量”的替代品。

## 关键语义高亮

- `<strong>` 只承载可独立扫描的工程结论：职责边界、唯一所有权、失败条件、验收限制、不可逆操作，或“为什么不可缺”的直接判断；它不是普通术语、文件名或整段话的装饰性加粗。
- 正文中的 `<strong>` 必须同时通过字重、前景/低强度底色和青绿色下划线形成层级，在默认深色与可选浅色主题中都能一眼区别于周围正文。任何一项单独存在都不足以视为合格高亮。
- `.notice` 与 `.deep-callout` 内的 `<strong>` 表示更高风险的约束或决策，必须以琥珀色下划线和更强字重高于普通结论；仅在确有警示语义时使用，不能把整个提示块全部标黄。
- `code` 只表示 API、类型、路径、配置键或命令。它应以等宽字体、细边框和低强度底色区分，但不得与结论高亮共享下划线或警示色，避免读者把标识符误读为判断。
- 禁止高亮整段、连续多句或每个技术名词。一个段落通常保留零至两个结论高亮；需要呈现完整限制时使用提示块或小节，而不是扩大高亮范围。
- 高密度对比矩阵必须显式区分“对象/角色”“获得的工作杠杆”和“仍需承担的责任”，不能让四列正文共享同一颜色、字重和节奏。长表滚动时表头必须保留当前列语义；手机端允许横向浏览，但不得把列硬压到不可读宽度。
- 带 `#锚点` 的直接打开、刷新、前进/后退，以及目录/TOC 的章节跳转，都必须立即落到目标标题下方，不能继承全局平滑滚动而出现空白过渡区或半程画面。每次改动导航后，至少直接打开一个章节锚点进行桌面与手机复核。
- 文档交付前必须扫描并清除解释正文、表格和导航中面向读者的未解析占位符，包括 `undefined`、`null`、`[object Object]`、模板变量残片及空链接文本。可折叠的逐字源码证据中出现的模板变量或语言字面量必须保留，但不得被误当成解释性内容。诊断列必须给出命名的入口、状态或证据链；不能用泛泛的“看日志”替代，也不能在缺值时渲染占位符。

## 内容单元标准

功能说明至少回答以下问题中的四项，且必须包含“它为什么不可缺”：

1. 它解决的工程问题和职责边界。
2. 运行或制作时的真实链路，以及谁拥有创建、取消和释放权。
3. 不使用它时传统 Unity/脚本式方案在哪个具体环节失控。
4. 改动它会影响的相邻模块、资产、工具或验收项。
5. 失败时的定位顺序，以及最低验证证据。

对比不能写成“ES 更好”。必须列出传统方案的隐式假设、ES 显式化的契约、获得的确定性和引入的维护成本。

## 更新验收

每次改版或新增章节后，至少确认：

- 桌面 `1440px` 和窄屏 `390px` 截图中标题、段落、表格和工具按钮均未裁切或重叠。
- 桌面正文宽度处于规定范围，多列表格无需在宽屏横向滚动；右侧来源栏出现时只包含实际文件入口。
- 所有 `href="#..."` 均有唯一目标，且没有外部 CSS 或 JavaScript 依赖。
- 默认主题为深色；目录菜单与主题切换在手机上可用。
- 宽屏与 `390px` 窄屏各抽查至少一段普通结论、一个 `.notice` / `.deep-callout` 约束以及一个 `code` 标识符：三者必须可区分、无裁切、无换行背景断裂导致的误读。
- 新增文字是解释、流程或验收结论，而不是未消化的源码转储。
- 修改 HTML 后同步更新 `DOCUMENT_SYNC.json` 的文件哈希和大小，以及 `DOCUMENT_SYNC.md` 的记录；不要以视觉更新推进源码审阅基线。
- 涉及源码行为的 HTML 更新必须对应一个 `ready-for-html` 的本地更新批次；批次条目、回归证据、已知缺口与 HTML 目标必须完整，再统一写入文档。仅有 Git diff 或局部完成口头说明时，继续记录在台账，不提前扩写 HTML。
